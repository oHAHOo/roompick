# 인기 숙소 응답 캐시 TTL 60초 의사결정

## 1. 문서 목적

이 문서는 인기 숙소 TOP N 응답 캐시에 TTL 60초를 적용한 이유와 허용하는 최신성 범위,
즉시 캐시 무효화가 필요한 상황, 현재 결정의 한계를 정리한다.

기존 인기 숙소 캐시 구조와 성능 결과는 다음 문서를 함께 참고한다.

- [`POPULAR_ACCOMMODATION_CACHE_DECISION.md`](POPULAR_ACCOMMODATION_CACHE_DECISION.md)
- [`POPULAR_ACCOMMODATION_CACHE.md`](POPULAR_ACCOMMODATION_CACHE.md)
- 이슈 `#109` — 인기 숙소 응답 캐시 Stampede 재현 및 단일 갱신 제어

## 2. 현재 정책

인기 숙소 응답 캐시는 다음 조건을 포함한 키별로 Redis에 저장한다.

```text
조회 기간 + 기간 기준 날짜 + limit
```

예시는 다음과 같다.

```text
popularAccommodations::
roompick:popular:accommodations:daily:2026-08-05:10
```

현재 기본 TTL은 60초다.

```text
캐시 HIT
→ 완성된 인기 숙소 DTO 목록 반환
→ Redis 랭킹 조회 생략
→ MySQL ACTIVE 숙소 조회 생략
→ 순서 복원과 DTO 재생성 생략
```

캐시가 만료된 뒤 최초 요청은 최신 랭킹 원본을 조회해 TOP N 응답을 다시 만들고
60초 동안 저장한다.

## 3. 왜 인기 숙소에는 짧은 최신성 지연을 허용할 수 있는가

인기 숙소 순위는 예약 가능 여부, 결제 금액, 재고처럼 거래 성공 여부를 결정하는 데이터가
아니다. 순위 반영이 잠시 늦어져도 중복 예약이나 금전 정합성 오류가 발생하지 않는다.

```text
예약 가능 여부가 오래된 경우
→ 이미 예약된 객실을 예약 가능하다고 판단할 수 있음
→ 거래 정합성 문제

인기 숙소 순위가 최대 약 60초 오래된 경우
→ 최근 조회 점수의 순위 반영이 잠시 늦어짐
→ 거래 정합성에는 직접 영향 없음
```

따라서 RoomPick은 인기 숙소 순위에 대해 제한된 시간의 최신성 지연을 허용하고,
그 대가로 반복되는 Redis 랭킹 조회와 MySQL 조회를 줄인다.

## 4. 왜 60초를 초기값으로 선택했는가

60초는 업계 전체가 공통으로 사용하는 평균값이 아니다. 데이터 성격과 서비스 요구를
기준으로 정한 RoomPick의 초기 절충값이다.

### 4.1 최신성 측면

숙소 상세 조회가 성공하면 DAILY와 WEEKLY 랭킹 원본 점수는 즉시 증가한다. 이미 생성된
응답 캐시는 조회수 증가마다 삭제하지 않으므로 사용자에게 보이는 순위는 최신 랭킹과
최대 약 60초 차이가 날 수 있다.

인기 숙소 기능에서는 이 정도 지연을 허용할 수 있지만, 수 분에서 수십 분 이상 이전
순위를 계속 노출하는 것은 “오늘의 인기”와 “이번 주 인기”라는 기능 의미를 약하게 만들 수
있다. 60초는 최근 조회 흐름을 비교적 빠르게 반영할 수 있는 범위로 정했다.

### 4.2 성능 측면

캐시가 없으면 같은 TOP N 요청마다 다음 비용이 반복된다.

1. Redis Sorted Set 랭킹 조회
2. MySQL ACTIVE 숙소 일괄 조회
3. Redis 순서 기준 재정렬
4. 비공개·존재하지 않는 숙소 필터링
5. rank 재계산과 응답 DTO 생성

60초 동안 같은 기간·날짜·limit 결과를 공유하면 짧은 시간에 반복되는 동일 계산을
제거할 수 있다.

기존 로컬 성능 측정에서는 현재 DAILY 경로 기준으로 다음 결과를 확인했다.

| 지표 | 응답 캐시 비활성화 | Warm cache |
|---|---:|---:|
| 평균 응답시간 | 6.27ms | 1.31ms |
| 처리량 | 1,566.50 RPS | 7,166.16 RPS |
| 오류율 | 0% | 0% |

이 측정은 TTL 후보를 비교한 결과가 아니라, 현재 캐시 활성·비활성 경로의 성능 차이를
확인한 결과다. 따라서 60초가 최적값이라는 직접 증거로 표현하지 않는다.

### 4.3 운영 복잡성 측면

숙소 상세 조회가 발생할 때마다 인기 숙소 응답 캐시를 제거하면 순위는 더 빨리 반영할 수
있다. 하지만 상세 조회 트래픽이 많아질수록 캐시가 계속 무효화되어 적중률이 낮아지고,
원본 조회와 캐시 재생성 횟수가 증가한다.

RoomPick은 다음과 같이 변경 종류를 구분했다.

```text
조회수 증가에 따른 순위 변화
→ 거래 정합성에 직접 영향 없음
→ 매번 evict하지 않고 TTL 만료로 반영

숙소 비공개 전환 또는 공개 정보 변경
→ 오래된 숙소 정보가 사용자에게 노출될 수 있음
→ TTL을 기다리지 않고 관련 인기 숙소 캐시 즉시 evict
```

이를 통해 빈번한 조회수 변경에는 단순한 TTL 정책을 사용하고, 사용자 노출 정확성에
중요한 변경은 명시적 무효화로 처리한다.

## 5. 왜 더 짧게 설정하지 않았는가

TTL을 10초 또는 30초로 줄이면 최근 랭킹이 더 빠르게 반영될 수 있다. 하지만 다음 비용이
증가한다.

- Cache Miss 증가
- Redis 랭킹 조회 증가
- MySQL 조회 증가
- DTO 재생성 증가
- 캐시 만료 시점 증가
- 만료 직후 동시 요청에 따른 Cache Stampede 발생 기회 증가

현재는 인기 순위를 수 초 단위로 갱신해야 한다는 제품 요구가 없으므로, 더 짧은 TTL을
선택해 원본 조회를 늘릴 이유가 충분하지 않다고 판단했다.

## 6. 왜 더 길게 설정하지 않았는가

TTL을 3분, 5분 또는 그 이상으로 늘리면 캐시 적중률이 높아지고 원본 조회 횟수는 더
줄어들 수 있다. 반면 캐시 생성 직후 순위가 변경되면 사용자에게 오래된 TOP N이 TTL
기간만큼 유지될 수 있다.

인기 숙소는 최근 관심 흐름을 보여주는 기능이므로, 초기 구현에서는 성능 이득을 더
확대하기보다 최대 반영 지연을 약 1분으로 제한하는 쪽을 선택했다.

장시간 TTL이 반드시 잘못된 것은 아니다. 실제 트래픽에서 60초와 180초 또는 300초의
성능 차이가 크고, 사용자가 수 분의 지연을 허용할 수 있다는 근거가 확인되면 재검토할 수
있다.

## 7. TTL과 즉시 무효화의 역할 구분

TTL은 모든 정합성 문제를 해결하는 수단이 아니다.

| 상황 | 처리 방식 | 이유 |
|---|---|---|
| 상세 조회수 증가 | 60초 TTL 만료로 반영 | 빈번하며 거래 정합성에 직접 영향 없음 |
| DAILY 날짜 변경 | 새 날짜 랭킹·캐시 키 사용 | 이전 날짜 데이터와 분리 |
| WEEKLY 주간 변경 | 새 주 시작일 랭킹·캐시 키 사용 | 이전 주 데이터와 분리 |
| 숙소 비공개 전환 | 관련 응답 캐시 즉시 evict | 비공개 숙소 노출 방지 |
| 공개 숙소 정보 수정 | 관련 응답 캐시 즉시 evict | 오래된 공개 정보 노출 방지 |
| Redis 장애 | 최신 ACTIVE 숙소 DB fallback | 인기 API 전체 장애 방지 |

응답 캐시 TTL은 완성된 응답을 얼마나 오래 재사용할지를 결정한다. 랭킹 원본의 DAILY와
WEEKLY 기간 정책은 어떤 조회 점수를 순위 계산에 포함할지를 결정한다. 두 설정은 서로
다른 문제를 해결한다.

## 8. 현재 결정의 한계

현재 60초는 캐시 적용 전후의 성능 측정과 인기 숙소 데이터의 최신성 요구를 바탕으로 정한
초기 정책이다. 다음 항목은 아직 별도 비교 측정이 필요하다.

- TTL 30초·60초·180초·300초의 Cache Hit/Miss 비교
- TTL별 Redis 랭킹 조회와 MySQL SELECT 횟수 비교
- TTL별 평균·p95·p99 응답시간 비교
- 랭킹 원본 변경부터 API 응답 변경까지의 실제 반영 지연 비교
- 캐시 만료 직후 동시 요청에서 중복 캐시 생성 여부
- 단일 갱신 제어 적용 전후의 원본 조회 감소 효과

따라서 현재 문서에서는 60초를 최적값으로 단정하지 않는다. 실제 트래픽과 동일 조건
실험 결과에 따라 조정할 수 있는 운영 설정으로 관리한다.

## 9. 다음 검증 — Cache Stampede

TTL이 짧을수록 캐시가 만료되는 횟수가 늘어난다. 캐시가 만료된 직후 같은 키로 여러
요청이 들어오면 각 요청이 동시에 Cache Miss를 확인하고 동일한 Redis 랭킹 조회와
MySQL 조회를 반복할 가능성이 있다.

```text
캐시 만료
→ 동일 키 동시 요청
→ 여러 요청이 Cache Miss 확인
→ 동일 원본 조회 반복 가능
→ 동일 응답 캐시 중복 생성 가능
```

이 문제는 이슈 `#109`에서 다음 순서로 검증한다.

1. Cold cache 상태에서 동일 키 동시 요청 재현
2. Redis 랭킹 조회, MySQL SELECT, 캐시 생성 횟수 측정
3. 실제 비용이 미미한지 또는 개선이 필요한지 판단
4. `@Cacheable(sync = true)`, Key 단위 Single Flight, Redis 분산 락 비교
5. 현재 배포 구조에 필요한 최소 복잡도의 방식 선택
6. 적용 전후를 동일한 조건으로 재측정

문제가 재현되지 않거나 비용이 미미하면 불필요한 락을 추가하지 않고 미적용 이유를
문서화한다. 문제가 유의미하면 하나의 요청만 캐시를 갱신하도록 개선한다.

## 10. 결론

RoomPick은 인기 숙소 응답 캐시에 60초 TTL을 적용하여 반복 조회 비용을 줄이면서도,
최근 인기 흐름의 반영 지연을 최대 약 1분으로 제한했다.

이 결정의 핵심은 다음과 같다.

```text
조회수 변화
→ 짧은 최신성 지연 허용
→ 60초 TTL로 반영

숙소 공개 상태·공개 정보 변경
→ 사용자 노출 정확성 중요
→ 즉시 캐시 무효화
```

60초는 업계 평균을 복사한 값이 아니라 RoomPick의 데이터 특성과 현재 요구를 바탕으로
선택한 초기값이다. 향후 TTL 후보 비교와 Cache Stampede 측정 결과를 통해 유지하거나
조정한다.
