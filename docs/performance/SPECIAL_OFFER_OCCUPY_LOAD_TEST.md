# 특가 점유 요청 부하 테스트 (한계점 탐색)

이슈 #131 "k6 기반 부하 테스트" 항목의 실행 기록이다. `docs/performance/SPECIAL_OFFER_QUEUE_ORDERING.md`가
순서 보장 방법론과 최초 30 VU 결과를 다뤘다면, 이 문서는 **VU 수를 단계적으로 늘려가며
실제로 어디서 한계에 부딪히는지**를 기록한다.

## 1. 측정 환경

운영 배포 문서(`docs/DEPLOYMENT.md`)의 EC2 `t3.small`(2vCPU/2GB, 앱+Prometheus+Grafana+Redis
공유)를 기준으로 삼되, **Kafka 브로커의 운영 메모리 배치는 이 문서에 정의되어 있지 않다**
([[project-kafka-consumer-group-sizing]] 메모 참고). 그래서 실제 운영값을 그대로 재현할 수
없었고, 대신 `t3.micro` 수준을 가정한 보수적 임의 제한값으로 전체 스택을 제한했다 — 아래
수치는 실측이지만 제한값 자체는 운영에서 확정된 값이 아닌 추정치다.

| 구성요소 | 메모리 제한 | 방식 |
|---|---:|---|
| MySQL 8.4 | 512MB | `docker update --memory` |
| Redis | 128MB | `docker update --memory` |
| Kafka (apache/kafka:3.8.0, 파티션 3) | 512MB (힙 256MB) | `KAFKA_HEAP_OPTS=-Xmx256m -Xms256m` |
| 애플리케이션 (컨슈머 concurrency=3) | JVM 힙 512MB | `JAVA_TOOL_OPTIONS=-Xmx512m -Xms256m` (호스트에서 직접 실행, 컨테이너화 안 함 — 힙만 제한) |

k6는 `grafana/k6` Docker 이미지로 실행했고, 매 단계마다 **새 객실 + 새 특가 상품**을 등록해
"정확히 1명만 HOLD를 받는가"를 매번 독립적으로 재검증했다 (같은 특가를 재사용하면 이미
승자가 정해져 있어 안전성 검증 의미가 없어짐).

측정 스크립트: `performance/k6/special-offer-occupy-stampede.js`. VU 수가 커지면 `setup()`의
순차 회원가입·로그인이 k6 기본 60초 제한을 넘길 수 있어 `setupTimeout`을 600초로 늘렸다
(이건 서버 성능과 무관한 k6 클라이언트 측 제약이다).

## 2. 단계별 결과

각 단계는 서로 다른 특가 상품에 대해 실행했고, k6 종료 직후 컨슈머가 전체 메시지를
처리(`waitlists` 행 수 == VU 수)할 때까지 폴링해서 **드레인 완료 후의 최종 상태**를 기록했다.

| VU | 202 성공률 | 오류율 | 평균 | p95 | p99 | max | 드레인 소요 | HOLD/WAIT | 비고 |

| 100 | 100% | 0% | 108ms | 192ms | 221ms | 231ms | 1.85s | 1 / 99 | |
| 300 | 100% | 0% | 152ms | 413ms | 470ms | 536ms | 4.65s | 1 / 299 | |
| 600 | 100% | 0% | 216ms | 643ms | 761ms | 913ms | 10.3s | 1 / 599 | |

## 3. 2000 VU에서 발생한 문제

1건이 `dial: i/o timeout`으로 실패했다 — 애플리케이션이 에러 응답을 준 게 아니라, k6
컨테이너가 애초에 TCP 연결 자체를 못 맺었다. 이 요청은 서버에 도달하지 않았으므로 Kafka에
이벤트가 발행되지 않았고, `waitlists`에도 영원히 나타나지 않는다 (드레인 대기가 120초
타임아웃까지 1999/2000에서 멈춘 이유).

이건 애플리케이션이나 컨슈머의 버그가 아니라, **2000개의 동시 아웃바운드 연결을 순간적으로
만드는 클라이언트(k6 컨테이너) 또는 그 경로의 네트워크 스택(Docker Desktop의
`host.docker.internal` 브리지, OS 임시 포트 한도 등)이 감당 범위 경계에 온 것**으로 보인다.
1000 VU까지는 정확히 0건 실패였고, 2000에서 처음이자 유일하게 1건만 실패한 것도 이 해석과
일치한다 — 서버·DB·Kafka가 뻗은 정황(컨테이너 재시작, OOM, 에러 로그)은 전혀 없었다.

부하 종료 후 컨테이너 상태:

```
roompick-mysql   464.8MiB / 512MiB (90.78%)
roompick-redis   9.977MiB / 128MiB (7.79%)
roompick-kafka   363.3MiB / 512MiB (70.96%)
```

세 컨테이너 모두 크래시나 OOM 없이 제한 안에서 살아있었고, 앱도 부하 직후 정상 응답
(`GET /api/v1/accommodations` → 200)했다. **메모리 제한 자체는 2000 VU까지도 한계에
부딪히지 않았다** — 병목은 메모리가 아니라 순간적인 대량 연결 생성 쪽에서 먼저 드러났다.

## 4. 안전성 — 모든 단계에서 정확히 1명만 HOLD

VU 수와 무관하게 모든 단계에서 `HOLD` 1건, 나머지는 전부 `WAIT`였다. 2000 VU 단계에서도
실패한 1건을 제외한 1999건이 정확히 1 HOLD + 1998 WAIT로 처리됐다 — 대량 동시 요청
상황에서도 중복 점유는 한 번도 발생하지 않았다.

## 5. 해석과 한계

- **처리량 자체의 명확한 한계는 이번 측정에서 찾지 못했다.** 1000 VU까지 완전 무결점,
  2000 VU에서 0.05% 오류가 클라이언트 연결 단계에서 발생했을 뿐 서버 쪽 자원(메모리, DB,
  Kafka)은 여유가 있었다. 더 높은 VU(5000, 10000 등)나 지속 부하(짧은 burst가 아닌 장시간
  유지)로 밀어붙이면 다른 지점에서 진짜 한계(MySQL 512MB 초과로 인한 OOM-kill, Kafka 컨슈머
  랙 무한 증가 등)가 나올 가능성이 있으나 이번 측정 범위에는 포함하지 않았다.
- 응답시간(p95/p99)은 VU 수에 거의 선형으로 증가했다(100 VU p95 192ms → 1000 VU p95
  913ms). 이는 애플리케이션이 감당 못 해서가 아니라, 모든 VU가 거의 동시에 요청을 쏘는
  burst 특성상 Tomcat 스레드 풀·커넥션 큐에서 대기하는 시간이 늘어난 것으로 보인다 —
  실제 스레드 풀 크기·큐 길이는 이번에 별도로 계측하지 않았다.
- 드레인 소요 시간도 VU 수에 거의 선형(100 VU 1.85s → 1000 VU 15.8s)으로 늘었다. 이는
  파티션당 컨슈머 1개가 순차 처리(각 처리당 DB 락 획득 포함)하는 구조이므로 당연한
  결과다 — 처리량을 늘리려면 파티션·컨슈머 수를 늘리는 게 다음 단계 검토 대상이다
  ([[project-kafka-consumer-group-sizing]] 참고, 아직 미확정).
- k6 컨테이너와 앱이 같은 로컬 머신을 공유하므로, 순수 네트워크 왕복 비용이나 k6 자체의
  리소스 경합이 결과에 섞여 있을 수 있다. 별도 부하 발생 머신에서 재측정하면 다른 숫자가
  나올 수 있다.
- 2000 VU의 1건 실패가 서버/네트워크 어느 쪽 한계인지 더 정확히 구분하려면 k6 쪽 커넥션
  설정(예: `http.batch`, keep-alive, `noConnectionReuse`)을 조정하며 재현해봐야 하는데
  이번 범위에는 포함하지 않았다.

## 6. 다중 특가 동시 진행 시나리오 (30개 특가 동시 처리)

"특가가 동시에 30개 열리면 컨슈머를 몇 개로 늘려야 하는가"라는 질문에 답하기 위해,
파티션 키가 `offerId`라는 점을 고려해 **여러 특가에 부하를 분산**하는 별도 스크립트
(`performance/k6/special-offer-multi-occupy-stampede.js`)로 재측정했다. 특가 30개를
동시에 등록하고 특가당 20명씩(총 600건) 점유 요청을 보냈다.

### 6.1 기존 설정 (파티션 3 / 컨슈머 concurrency 3 / Hikari 기본 풀 10)

컨슈머 로그에서 각 특가를 실제로 처리한 스레드를 역추적한 결과:

```
ntainer#0-0-C-1: 13개 특가 담당
ntainer#0-1-C-1: 13개 특가 담당
ntainer#0-2-C-1:  4개 특가 담당
```

파티션이 3개뿐이라 `offerId` 해시가 균등하게 안 퍼지고 **13/13/4로 불균등하게
몰렸다** — 파티션 하나에 특가 13개가 몰리면, 그 13개는 서로의 처리 순서를
기다리며 지연이 커질 수 있다는 뜻이다. 이 규모(600건)에서는 처리 자체는
100% 성공, 0% 오류, 드레인 1초로 문제없었지만 **분산이 이론상 불균등했다.**

### 6.2 확장 설정 (파티션 60 / 컨슈머 concurrency 10 / Hikari 풀 15)

```yaml
# KafkaTopicConfig.java: partitions(3) → partitions(60)
# OfferOccupyEventConsumer: concurrency = "3" → "10"
# application-local.yml: hikari.maximum-pool-size: 15 (신규 추가, 이전엔 기본값 10)
```

기존 토픽에 파티션을 60개로 선언하고 재기동하니 Spring Kafka `KafkaAdmin`이
**기존 파티션 수를 자동으로 3 → 60으로 늘려줬다** (`kafka-topics.sh --describe`로
확인). 같은 30개 특가·600건 부하를 다시 측정한 결과:

```
컨슈머 스레드 10개에 특가 1~5개씩 분산 (최대 5개, 기존 최대 13개 대비 크게 개선)
```

처리 자체는 이번에도 100% 성공, 0% 오류, 드레인 1초로 기존 설정과 큰 차이는
없었다(이 규모에선 기존 설정도 이미 여유가 있었으므로). **하지만 분산은 명확히
개선됐다** — 특가 하나가 다른 특가 12개 뒤에 밀려서 대기하는 최악의 경우가
사라지고, 최대 대기 폭이 5개로 줄었다.

### 6.3 예상치 못한 부작용 — MySQL 메모리 압박

확장 설정으로 재측정한 직후 `docker stats`에서 MySQL 메모리 사용량이
**504.1MiB/512MiB (98.45%)**까지 올라갔다 (기존 설정 측정 시점엔 90%대였다).
컨테이너가 크래시하거나 재시작되지는 않았지만, 512MB 제한 안에서 **여유가
매우 적어졌다.**

원인으로 추정되는 것: Hikari 풀을 10 → 15로 늘리면 MySQL 서버 쪽에서
동시에 유지해야 하는 커넥션 수와 그에 따른 세션 버퍼 메모리가 함께
늘어난다. 컨슈머 concurrency를 늘려 파티션 분산을 개선한 대가로, **DB
메모리 여유가 줄어드는 트레이드오프가 실제로 관측됐다** — 이건 이번 세션
전까지는 예상만 했지 실측하지 못했던 부분이다.

### 6.4 결론 — 컨슈머 수를 어떻게 정할지에 대한 근거

- **파티션 수는 예상 동시 진행 특가 수보다 넉넉히 크게 잡아야 한다.** 30개
  특가에 파티션 3개는 명확히 부족했고(13/13/4 불균등), 60개로 늘리자
  1~5개로 고르게 퍼졌다. 예상 동시 특가 수의 2배 이상을 권장값으로 삼을 만하다.
- **컨슈머 concurrency와 Hikari 풀 크기는 같이 움직여야 하고, DB 메모리
  여유와 맞바꾸는 트레이드오프다.** 컨슈머를 늘려 파티션 분산·병렬 처리를
  개선하면 그만클 DB 커넥션도 늘어야 하는데, 지금처럼 MySQL 자체도
  메모리 제한(512MB, 이것도 운영 확정치가 아닌 추정치)이 걸려 있으면
  Hikari 풀을 무작정 키울 수 없다.
- **운영에 적용하기 전에 반드시 확인해야 할 것**: 운영 DB(RDS `db.t4g.micro`,
  `docs/DEPLOYMENT.md` 기준)의 실제 메모리 여유와 `max_connections` 설정을
  먼저 확인하고, 거기에 맞춰 Hikari 풀·컨슈머 concurrency 상한을 역산해야
  한다. 이번 로컬 측정(512MB 임의 제한)은 방향성 확인용이지 운영 수치의
  대체재가 아니다.
