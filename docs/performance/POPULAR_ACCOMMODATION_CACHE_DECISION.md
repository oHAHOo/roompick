# 인기 숙소 응답 캐시 의사결정

## 1. 배경

인기 숙소 TOP N은 홈·탐색 화면에서 여러 사용자가 반복해서 조회하는 읽기 중심 기능이다.
예약이나 결제와 달리 짧은 시간 동안 순위 반영이 늦어져도 거래 정합성을 훼손하지 않는다.
이 문서는 인기 숙소에 Redis 응답 캐시를 적용한 이유와 V1의 한계, 이후 기간별 랭킹으로
고도화한 방향을 설명한다. 측정 절차와 원본 수치는
[`POPULAR_ACCOMMODATION_CACHE.md`](POPULAR_ACCOMMODATION_CACHE.md)에 분리한다.

## 2. 문제 정의

응답 캐시가 없으면 같은 TOP N 요청마다 다음 작업이 반복된다.

1. Redis Sorted Set에서 인기 숙소 ID 구간 조회
2. MySQL에서 ACTIVE 숙소 공개 정보 조회
3. Redis 랭킹 순서 복원과 비공개 숙소 필터링
4. 연속 순위 부여와 응답 DTO 목록 생성

조회자마다 결과가 대부분 같은데도 이 비용을 매번 지불하는 것이 문제였다.

## 3. 왜 인기 숙소 TOP N을 캐시 대상으로 선택했는가

- 홈·탐색 화면에서 호출 빈도가 높을 가능성이 있다.
- 여러 사용자가 같은 기간·날짜·limit 결과를 공유한다.
- 쓰기보다 읽기가 많다.
- 최대 20개의 작은 응답이며 재사용 가치가 높다.
- 최대 60초의 순위 지연을 허용할 수 있다.

따라서 개별 JPA Entity가 아니라 순서와 rank까지 완성된
`List<PopularAccommodationResponseDto>` 전체를 Redis에 저장한다. 캐시 HIT에서는
랭킹 조회, DB 조회, 순서 조합과 DTO 재생성을 모두 생략할 수 있다.

## 4. 다른 기능에는 왜 적용하지 않았는가

이번 캐시 대상은 인기 숙소 TOP N API뿐이다. 숙소 상세, 객실 조회, 예약, 결제,
회원, 관리자 기능에는 이 응답 캐시를 적용하지 않았다. 특히 예약·결제는 최신 상태와
강한 정합성이 중요하므로 인기 순위와 같은 TTL 기반 최신성 절충을 그대로 적용할 수 없다.
숙소 상세 조회는 응답 캐시 대상이 아니라 인기 점수를 만드는 이벤트다.

## 5. V1 구조

제품 발전 시나리오에서 V1은 서비스 출시 이후 전체 누적 상세 조회수를 Sorted Set에
기록하고 TOP N을 선정하는 구조로 정의한다. V1 응답 캐시의 목적은 누적 랭킹을 계산하는
방식을 바꾸는 것이 아니라 동일 결과의 반복 조회 비용을 제거하는 것이었다.

```text
상세 조회 성공 → 누적 인기 점수 증가
인기 숙소 조회 → 랭킹 원본 조회 → ACTIVE 숙소 DB 조회 → TOP N DTO 생성 → 응답 캐시
```

## 6. 현재 구현에서 랭킹 원본과 응답 캐시의 차이

아래 DAILY/WEEKLY 키는 현재 구현 기준이다. 제품 발전 시나리오의 V1은 기간 구분 없는
전체 누적 조회수를 랭킹 원본으로 사용한다고 가정한다. V1 시나리오와 현재 코드 구조를
혼동하지 않도록 두 관점을 명확하게 구분한다.

두 Redis 데이터는 역할이 다르다.

### 인기 숙소 랭킹 원본

```text
roompick:popular:accommodations:daily:2026-08-04
roompick:popular:accommodations:weekly:2026-08-03
```

- Redis Sorted Set
- member는 숙소 ID, score는 상세 조회 점수
- 어떤 숙소가 인기 있는지를 결정하는 원본 데이터
- 인기 숙소 목록 조회 자체는 점수를 증가시키지 않음

### 인기 숙소 API 응답 캐시

```text
popularAccommodations::roompick:popular:accommodations:daily:2026-08-04:10
```

- 완성된 인기 숙소 응답 DTO 목록 전체
- 동일 기간·기준 날짜·limit 요청에서 랭킹 및 DB 조회를 생략
- 랭킹 원본을 대체하지 않으며 TTL 만료 후 원본으로 다시 생성

## 7. 캐시 키 설계

응답 캐시 키는 기간, 기간별 기준 날짜, limit을 포함한다.

```text
popularAccommodations::{ranking-key}:{limit}
```

따라서 DAILY와 WEEKLY, 서로 다른 날짜, 서로 다른 limit은 각각 독립된 캐시 항목이다.
기본 API limit은 10이고 허용 범위는 1 이상 20 이하이다.

## 8. TOP N 및 limit별 캐시 동작

`limit=10` 최초 요청은 TOP 10 전체를 조회하고 DTO 목록 전체를 `...:10` 키에 저장한다.

`limit=20` 최초 요청은 기존 TOP 10 캐시에서 11~20위만 이어 붙이지 않는다. TOP 20
전체를 다시 조회하고 DTO 목록 전체를 별도 `...:20` 키에 저장한다.

```text
...:10 → 1위부터 10위까지
...:20 → 1위부터 20위까지
```

일부 DTO가 중복 저장되지만 최대 20개이고 TTL이 60초다. 부분 캐시 조합과 무효화
복잡성을 만들기보다 limit별 완성 응답을 분리하는 단순하고 안전한 방식을 선택했다.

## 9. TTL 60초 선택에 따른 성능과 최신성의 절충

사용자가 숙소 상세 페이지를 정상 조회하면 DAILY와 WEEKLY 랭킹 원본 점수가 즉시
증가한다. 반면 이미 생성된 TOP N 응답 캐시는 조회 점수 증가만으로 삭제하지 않고
남은 TTL 동안 유지한다. 따라서 사용자에게 보이는 목록은 최신 랭킹과 최대 약 60초
차이가 날 수 있다. 만료 후 첫 요청이 최신 랭킹을 기준으로 TOP N 전체를 다시 만들고
캐싱한다. 인기 숙소 API 호출 자체는 인기 점수를 증가시키지 않는다.

## 10. 정량적 성능 개선 결과

현재 측정은 2026-08-04 로컬 macOS에서 DAILY, `limit=5`, 10 VU, 30초 조건으로
수행했다. 누적 조회수 기반 V1을 별도로 직접 측정한 결과는 아니다.

| 지표 | 응답 캐시 비활성화 | Warm cache |
|---|---:|---:|
| 평균 응답시간 | 6.27ms | 1.31ms |
| 처리량 | 1,566.50 RPS | 7,166.16 RPS |
| 오류율 | 0% | 0% |

이 환경에서는 평균 응답시간이 약 79.1% 감소하고 처리량이 약 4.57배 증가했다.
Warm cache의 MySQL SELECT는 0회, Cold cache는 1회였다. Redis 장애에서도 DB
fallback으로 오류율 0%와 HTTP 200을 유지했지만 평균 67.22ms, 148.10 RPS로
성능이 크게 낮아졌다.

## 11. V1에서 예상되는 장기 운영 한계

누적 조회수 원본은 과거의 인기를 계속 포함한다. 시간이 지나면 과거에 높은 점수를 얻은
숙소가 상위에 오래 남고 최근 관심을 받는 신규 숙소는 진입하기 어려워진다.

문제는 오래된 숙소가 Redis **응답 캐시**에 계속 남는 것이 아니다. 응답 캐시가
만료되어도 전체 누적 조회수 기반 **랭킹 원본**을 다시 조회하므로 같은 과거 인기 숙소가
TOP N으로 재선정되어 다시 캐싱되는 것이다. 즉 원인은 TTL이 아니라 순위를 계산하는
원본 데이터의 시간 범위다.

## 12. V2 고도화 방향

V2의 목적은 캐시 적중률 개선이 아니라 최근 인기 흐름을 순위에 반영하는 것이다.

- 일간·주간 조회수 기반 랭킹
- 기간별 Redis Sorted Set 키 분리
- 기간과 기준 날짜를 포함한 응답 캐시 키
- 최근 인기 숙소와 신규 숙소의 진입 가능성 개선
- V1 누적 순위와 V2 기간별 순위의 최신성 비교

## 13. 현재 코드 상태와 발표 버전 구분

제품 발전 설명의 V1은 누적 조회수 기반 TOP N에 응답 캐시를 도입한 의사결정 단계다.
현재 `develop` 기반 코드에는 DAILY/WEEKLY 기간별 랭킹과 기간별 캐시 키 구조가
기술적으로 먼저 반영되어 있으며, 이 사실과 실제 git 이력·구현 시점은 그대로 유지한다.

이번 성능 결과는 현재 코드의 `period=DAILY` 경로에서 응답 캐시 활성/비활성을 비교한
것이다. 그러므로 이 수치를 “누적 조회수 기반 V1을 직접 측정한 결과”로 표현하지 않는다.
이번 V1 문서는 응답 캐시를 선택한 이유와 성능 효과를 다룬다. 누적 조회수 기반 순위의
최신성 문제 재현, 기간별 랭킹의 고도화 의사결정, V1과 V2의 순위 최신성 비교는
2026-08-05 이후 별도로 진행한다.

## 14. 결론

인기 숙소 TOP N은 공유도가 높고 읽기가 많으며 짧은 최신성 지연을 허용할 수 있어
완성된 응답 DTO 캐시에 적합했다. 응답 캐시는 반복되는 Redis 랭킹 조회와 MySQL 조회,
조합 비용을 줄였지만 인기 순위를 결정하는 원본의 시간 범위 문제는 해결하지 않는다.
V1의 성능 최적화와 V2의 기간별 최신성 개선은 서로 다른 문제를 해결하는 단계다.
