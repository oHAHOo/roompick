# 인기 숙소 응답 캐시 의사결정

## 1. 배경

인기 숙소 TOP N은 홈·탐색 화면에서 여러 사용자가 반복해서 조회하는 읽기 중심 기능이다.
예약이나 결제와 달리 짧은 시간 동안 순위 반영이 늦어져도 거래 정합성을 훼손하지 않는다.
이 문서는 인기 숙소에 Redis 응답 캐시를 적용한 이유와 V1의 한계, 이후 기간별 랭킹으로
고도화한 방향을 설명한다. 측정 절차와 원본 수치는
[`POPULAR_ACCOMMODATION_CACHE.md`](POPULAR_ACCOMMODATION_CACHE.md)에 분리한다.

## 2. 문제 정의

응답 캐시가 없으면 같은 TOP N 요청마다 다음 작업이 반복된다.

1. Redis Sorted Set에서 인기 숙소 ID 구간 조회
2. MySQL에서 ACTIVE 숙소 공개 정보 조회
3. Redis 랭킹 순서 복원과 비공개 숙소 필터링
4. 연속 순위 부여와 응답 DTO 목록 생성

조회자마다 결과가 대부분 같은데도 이 비용을 매번 지불하는 것이 문제였다.

## 3. 왜 인기 숙소 TOP N을 캐시 대상으로 선택했는가

- 홈·탐색 화면에서 호출 빈도가 높을 가능성이 있다.
- 여러 사용자가 같은 기간·날짜·limit 결과를 공유한다.
- 쓰기보다 읽기가 많다.
- 최대 20개의 작은 응답이며 재사용 가치가 높다.
- 최대 60초의 순위 지연을 허용할 수 있다.

따라서 개별 JPA Entity가 아니라 순서와 rank까지 완성된
`List<PopularAccommodationResponseDto>` 전체를 Redis에 저장한다. 캐시 HIT에서는
랭킹 조회, DB 조회, 순서 조합과 DTO 재생성을 모두 생략할 수 있다.

## 4. 다른 기능에는 왜 적용하지 않았는가

이번 캐시 대상은 인기 숙소 TOP N API뿐이다. 숙소 상세, 객실 조회, 예약, 결제,
회원, 관리자 기능에는 이 응답 캐시를 적용하지 않았다. 특히 예약·결제는 최신 상태와
강한 정합성이 중요하므로 인기 순위와 같은 TTL 기반 최신성 절충을 그대로 적용할 수 없다.
숙소 상세 조회는 응답 캐시 대상이 아니라 인기 점수를 만드는 이벤트다.

## 5. V1 구조

제품 발전 시나리오에서 V1은 서비스 출시 이후 전체 누적 상세 조회수를 Sorted Set에
기록하고 TOP N을 선정하는 구조로 정의한다. V1 응답 캐시의 목적은 누적 랭킹을 계산하는
방식을 바꾸는 것이 아니라 동일 결과의 반복 조회 비용을 제거하는 것이었다.

```text
상세 조회 성공 → 누적 인기 점수 증가
인기 숙소 조회 → 랭킹 원본 조회 → ACTIVE 숙소 DB 조회 → TOP N DTO 생성 → 응답 캐시
```

## 6. 현재 구현에서 랭킹 원본과 응답 캐시의 차이

아래 DAILY/WEEKLY 키는 현재 구현 기준이다. 제품 발전 시나리오의 V1은 기간 구분 없는
전체 누적 조회수를 랭킹 원본으로 사용한다고 가정한다. V1 시나리오와 현재 코드 구조를
혼동하지 않도록 두 관점을 명확하게 구분한다.

두 Redis 데이터는 역할이 다르다.

### 인기 숙소 랭킹 원본

```text
roompick:popular:accommodations:daily:2026-08-04
roompick:popular:accommodations:weekly:2026-08-03
```

- Redis Sorted Set
- member는 숙소 ID, score는 상세 조회 점수
- 어떤 숙소가 인기 있는지를 결정하는 원본 데이터
- 인기 숙소 목록 조회 자체는 점수를 증가시키지 않음

### 인기 숙소 API 응답 캐시

```text
popularAccommodations::roompick:popular:accommodations:daily:2026-08-04:10
```

- 완성된 인기 숙소 응답 DTO 목록 전체
- 동일 기간·기준 날짜·limit 요청에서 랭킹 및 DB 조회를 생략
- 랭킹 원본을 대체하지 않으며 TTL 만료 후 원본으로 다시 생성

## 7. 캐시 키 설계

응답 캐시 키는 기간, 기간별 기준 날짜, limit을 포함한다.

```text
popularAccommodations::{ranking-key}:{limit}
```

따라서 DAILY와 WEEKLY, 서로 다른 날짜, 서로 다른 limit은 각각 독립된 캐시 항목이다.
기본 API limit은 10이고 허용 범위는 1 이상 20 이하이다.

## 8. TOP N 및 limit별 캐시 동작

`limit=10` 최초 요청은 TOP 10 전체를 조회하고 DTO 목록 전체를 `...:10` 키에 저장한다.

`limit=20` 최초 요청은 기존 TOP 10 캐시에서 11~20위만 이어 붙이지 않는다. TOP 20
전체를 다시 조회하고 DTO 목록 전체를 별도 `...:20` 키에 저장한다.

```text
...:10 → 1위부터 10위까지
...:20 → 1위부터 20위까지
```

일부 DTO가 중복 저장되지만 최대 20개이고 TTL이 60초다. 부분 캐시 조합과 무효화
복잡성을 만들기보다 limit별 완성 응답을 분리하는 단순하고 안전한 방식을 선택했다.

## 9. TTL 60초 선택에 따른 성능과 최신성의 절충

사용자가 숙소 상세 페이지를 정상 조회하면 DAILY와 WEEKLY 랭킹 원본 점수가 즉시
증가한다. 반면 이미 생성된 TOP N 응답 캐시는 조회 점수 증가만으로 삭제하지 않고
남은 TTL 동안 유지한다. 따라서 사용자에게 보이는 목록은 최신 랭킹과 최대 약 60초
차이가 날 수 있다. 만료 후 첫 요청이 최신 랭킹을 기준으로 TOP N 전체를 다시 만들고
캐싱한다. 인기 숙소 API 호출 자체는 인기 점수를 증가시키지 않는다.

## 10. 정량적 성능 개선 결과

현재 측정은 2026-08-04 로컬 macOS에서 DAILY, `limit=5`, 10 VU, 30초 조건으로
수행했다. 누적 조회수 기반 V1을 별도로 직접 측정한 결과는 아니다.

| 지표 | 응답 캐시 비활성화 | Warm cache |
|---|---:|---:|
| 평균 응답시간 | 6.27ms | 1.31ms |
| 처리량 | 1,566.50 RPS | 7,166.16 RPS |
| 오류율 | 0% | 0% |

이 환경에서는 평균 응답시간이 약 79.1% 감소하고 처리량이 약 4.57배 증가했다.
Warm cache의 MySQL SELECT는 0회, Cold cache는 1회였다. Redis 장애에서도 DB
fallback으로 오류율 0%와 HTTP 200을 유지했지만 평균 67.22ms, 148.10 RPS로
성능이 크게 낮아졌다.

## 11. V1에서 예상되는 장기 운영 한계

누적 조회수 원본은 과거의 인기를 계속 포함한다. 시간이 지나면 과거에 높은 점수를 얻은
숙소가 상위에 오래 남고 최근 관심을 받는 신규 숙소는 진입하기 어려워진다.

문제는 오래된 숙소가 Redis **응답 캐시**에 계속 남는 것이 아니다. 응답 캐시가
만료되어도 전체 누적 조회수 기반 **랭킹 원본**을 다시 조회하므로 같은 과거 인기 숙소가
TOP N으로 재선정되어 다시 캐싱되는 것이다. 즉 원인은 TTL이 아니라 순위를 계산하는
원본 데이터의 시간 범위다.

## 12. V2 고도화 방향

V2의 목적은 캐시 적중률을 높이는 것이 아니라 최근 인기 흐름을 순위에 반영하는 것이다.

* 일간·주간 조회수 기반 랭킹
* 기간별 Redis Sorted Set 키 분리
* 기간과 기준 날짜를 포함한 응답 캐시 키
* 최근 인기 숙소와 신규 숙소의 진입 가능성 개선
* V1 누적 순위와 V2 기간별 순위의 최신성 비교

현재 운영 코드에는 DAILY/WEEKLY 랭킹이 이미 구현되어 있다. 이번 고도화에서는 운영
기능을 다시 구현하거나 `CUMULATIVE` 기간을 추가하지 않고, 누적 랭킹을 테스트 전용
V1 제품 시나리오로 재현해 현재 기간별 랭킹과 비교했다.

## 13. 최신성 비교 테스트 설계

비교 테스트는 다음 파일에 작성했다.

```text
src/test/java/com/roompick/domain/accommodation/repository/
PopularAccommodationRankingFreshnessIntegrationTest.java
```

Redis 7 Testcontainers 환경에서 실제 Sorted Set을 사용했으며, 운영 Redis 키와
충돌하지 않도록 V1 누적 랭킹은 다음 테스트 전용 키로 분리했다.

```text
roompick:test:popular:accommodations:cumulative
```

V1 누적 랭킹은 장기간 점수가 유지되는 상황을 재현해야 하므로 TTL을 설정하지 않았다.
DAILY/WEEKLY는 현재 운영 `PopularAccommodationKeyGenerator`의 키 규칙을 그대로
사용했다.

```text
roompick:popular:accommodations:daily:{기준 날짜}
roompick:popular:accommodations:weekly:{해당 주 월요일}
```

점수 구성은 테스트 목적에 맞게 `StringRedisTemplate`로 직접 입력하고, 순위 조회는
운영 코드와 동일한 `PopularAccommodationRankingRepository`를 공통으로 사용했다.

따라서 비교 대상 간 차이는 다음과 같다.

```text
V1 누적 랭킹
→ 과거와 현재 점수를 하나의 Sorted Set에 계속 누적
→ TTL 없음

V2 기간별 랭킹
→ DAILY/WEEKLY 기준 날짜마다 별도 Sorted Set 사용
→ 이전 기간 점수가 새 기간 키에 직접 포함되지 않음
```

이번 테스트는 응답시간이나 처리량을 다시 측정하는 성능 테스트가 아니라, 동일한 점수
조건에서 랭킹 원본의 시간 범위가 순위 최신성에 어떤 차이를 만드는지 검증하는 테스트다.

RoomPick의 사용자 노출 기준은 인기 숙소 TOP 10이다. 이번 테스트에서는 누적 점수가
최근 인기 숙소와 신규 숙소의 순위 진입에 미치는 영향을 명확하게 확인하기 위해 동일한
정렬 로직의 조회 범위를 TOP 2와 TOP 3으로 축소했다. Redis Sorted Set의 내림차순
조회 방식은 동일하므로 검증 결과는 TOP 10 조회에도 같은 원리로 적용된다.

## 14. 비교 시나리오와 결과

### 14.1 과거 인기 숙소 고착

다음 점수를 구성했다.

| 숙소              | V1 누적 점수 | DAILY 점수 |
| --------------- | -------: | -------: |
| 숙소 1 — 과거 인기 숙소 |    1,000 |        1 |
| 숙소 2 — 최근 인기 숙소 |      200 |       50 |
| 숙소 3 — 다른 최근 숙소 |      100 |       20 |

조회 결과는 다음과 같았다.

```text
V1 누적 순위
1위 숙소 1
2위 숙소 2
3위 숙소 3

V2 DAILY 순위
1위 숙소 2
2위 숙소 3
3위 숙소 1
```

누적 랭킹에서는 현재 조회가 거의 없는 숙소 1이 과거 점수 1,000으로 계속 1위를
유지했다. 반면 DAILY에서는 당일 조회가 집중된 숙소 2와 숙소 3이 숙소 1보다 앞섰다.

이 결과로 누적 랭킹은 과거 인기를 안정적으로 반영하지만 최근 관심 변화에 늦게
반응할 수 있다는 점을 확인했다.

### 14.2 신규 숙소의 TOP N 진입

기존 숙소 두 개와 신규 숙소 하나에 다음 점수를 구성했다.

| 숙소      | V1 누적 점수 | DAILY 점수 | WEEKLY 점수 |
| ------- | -------: | -------: | --------: |
| 기존 숙소 1 |    1,000 |        5 |        30 |
| 기존 숙소 2 |      900 |        3 |        20 |
| 신규 숙소 3 |       80 |      100 |       150 |

TOP 2 결과는 다음과 같았다.

```text
V1 누적 TOP 2
1위 기존 숙소 1
2위 기존 숙소 2
→ 신규 숙소 3 미진입

V2 DAILY TOP 2
1위 신규 숙소 3

V2 WEEKLY TOP 2
1위 신규 숙소 3
```

신규 숙소는 최근 조회가 가장 많았지만 누적 점수 격차 때문에 V1 TOP 2에는 진입하지
못했다. DAILY와 WEEKLY에서는 최근 점수만 비교하므로 모두 1위로 진입했다.

기간별 랭킹이 신규 숙소를 무조건 상위에 노출하는 것은 아니지만, 적어도 과거 누적
점수와 경쟁하지 않고 최근 사용자 관심을 기준으로 순위에 진입할 기회를 제공한다.

### 14.3 응답 캐시 제거 후 재선정

V1 누적 랭킹에 다음 순위를 구성했다.

```text
숙소 1: 1,000점
숙소 2: 800점
숙소 3: 500점
```

별도의 테스트용 응답 캐시 키를 생성한 뒤 삭제했다.

```text
popularAccommodations::
roompick:test:popular:accommodations:cumulative:3
```

응답 캐시 삭제 전후의 TOP 3는 모두 다음과 같았다.

```text
숙소 1 → 숙소 2 → 숙소 3
```

응답 캐시 키는 삭제됐지만 누적 랭킹 원본 Sorted Set은 그대로 남아 있었다. 따라서
캐시가 만료되거나 제거된 이후에도 같은 누적 랭킹을 다시 읽으면 과거 인기 숙소가
동일하게 TOP N으로 재선정된다.

이를 통해 다음 두 문제를 분리해서 확인했다.

```text
응답 캐시 TTL
→ 완성된 응답을 얼마 동안 재사용할지 결정

랭킹 원본의 시간 범위
→ 어떤 조회 점수를 순위 계산에 포함할지 결정
```

따라서 응답 캐시 TTL을 줄이거나 캐시를 자주 삭제하는 것만으로는 누적 랭킹의 최신성
문제를 해결할 수 없다.

### 14.4 DAILY와 WEEKLY 기간 경계

DAILY는 다음 두 날짜의 키를 분리했다.

```text
roompick:popular:accommodations:daily:2026-08-04
roompick:popular:accommodations:daily:2026-08-05
```

WEEKLY는 일요일과 다음 월요일을 기준으로 다음 키를 사용했다.

```text
roompick:popular:accommodations:weekly:2026-07-27
roompick:popular:accommodations:weekly:2026-08-03
```

이전 DAILY/WEEKLY 키에 숙소 1의 점수 1,000을 넣어도 새 기간의 랭킹은 비어 있었다.
새 기간 키에 숙소 2의 점수를 기록한 뒤에는 새 랭킹에 숙소 2만 포함됐다.

```text
이전 기간
숙소 1: 1,000점

새 기간 최초 조회
빈 랭킹

새 기간 점수 기록 후
숙소 2만 조회
```

기간 경계가 바뀌면 이전 기간 점수가 삭제되는 것이 아니라 새로운 키를 조회한다.
이전 데이터는 보관 정책과 TTL에 따라 일정 기간 남을 수 있지만, 새 기간의 순위에는
직접 포함되지 않는다.

## 15. V1과 V2 비교

| 항목       | V1 누적 랭킹        | V2 DAILY      | V2 WEEKLY        |
| -------- | --------------- | ------------- | ---------------- |
| 점수 범위    | 서비스 시작 이후 전체    | 당일            | 해당 주 월요일부터       |
| 과거 인기 유지 | 매우 강함           | 낮음            | DAILY보다 높음       |
| 최근 변화 반영 | 느림              | 가장 빠름         | 비교적 빠름           |
| 신규 숙소 진입 | 누적 격차로 어려울 수 있음 | 최근 조회가 많으면 가능 | 최근 주간 조회가 많으면 가능 |
| 기간 경계    | 없음              | 매일 변경         | 매주 월요일 변경        |
| 순위 안정성   | 높음              | 변동성이 큼        | DAILY보다 안정적      |
| 적합한 의미   | 장기 누적 인기        | 오늘의 인기        | 이번 주 인기          |

V1 누적 랭킹이 항상 잘못된 것은 아니다. 장기간 검증된 대표 숙소나 전체 기간 베스트를
보여주는 기능에는 누적 점수가 적합할 수 있다. 다만 이를 “현재 인기 숙소”로 제공하면
최근 관심 변화와 신규 숙소 진입을 충분히 반영하지 못할 수 있다.

DAILY는 최신성이 높지만 하루 단위로 점수가 초기화되는 효과가 있어 트래픽이 적은
시간대에는 표본이 부족하거나 순위 변동이 커질 수 있다. WEEKLY는 최근 흐름을
반영하면서 DAILY보다 점수를 안정적으로 축적할 수 있다.

RoomPick은 사용자에게 기간의 의미를 명확하게 제공하기 위해 현재 다음 두 조회 방식을
유지한다.

```text
DAILY
오늘 사용자들이 많이 조회한 숙소

WEEKLY
이번 주 사용자들이 많이 조회한 숙소
```

## 16. 현재 코드 상태와 제품 발전 설명

제품 발전 설명에서 V1은 전체 누적 조회수 기반 TOP N에 응답 캐시를 적용한 단계로
정의한다. V2는 누적 랭킹의 최신성 한계를 해결하기 위해 DAILY/WEEKLY 기간별 랭킹과
기간별 캐시 키를 사용한 단계다.

실제 Git 이력에서는 DAILY/WEEKLY 구조가 이 비교 테스트보다 먼저 구현됐다. 이번
작업은 이미 구현된 현재 구조를 과거 구조로 위장하거나 Git 이력을 변경하지 않는다.

2026-08-04 이슈 `#102`에서 누적 랭킹을 테스트 전용 제품 시나리오로 별도 재현하여,
V1과 현재 DAILY/WEEKLY 구조의 최신성 차이를 검증했다.

기존 성능 결과는 현재 코드의 `period=DAILY` 경로에서 응답 캐시 활성·비활성을 비교한
결과다. 해당 수치를 누적 조회수 기반 V1을 직접 측정한 결과로 표현하지 않는다.

또한 이번 비교 테스트는 기존 다음 성능 측정 원본을 수정하거나 다시 측정하지 않았다.

```text
performance/results/*.txt
performance/results/*.csv
```

따라서 두 결과의 역할은 다음과 같이 구분한다.

```text
기존 성능 테스트
→ 응답 캐시 적용 전후의 응답시간·처리량·DB 조회 감소 효과 검증

이번 최신성 비교 테스트
→ 누적·DAILY·WEEKLY 랭킹의 순위 반영 차이 검증
```

## 17. 결론

인기 숙소 응답 캐시는 반복되는 Redis 랭킹 조회, MySQL 조회, 순서 복원과 DTO 생성
비용을 줄인다. 하지만 응답 캐시는 이미 결정된 순위를 재사용할 뿐, 어떤 기간의 점수로
순위를 계산할지는 바꾸지 않는다.

누적 랭킹에서는 과거 인기 숙소가 응답 캐시 만료 이후에도 다시 TOP N으로 선정됐고,
최근 조회가 집중된 숙소와 신규 숙소가 높은 누적 점수에 밀릴 수 있었다.

DAILY와 WEEKLY 기간별 랭킹에서는 이전 기간 점수가 새 기간 순위에 직접 포함되지
않아 최근 관심을 받은 숙소와 신규 숙소가 순위에 진입할 수 있었다.

따라서 RoomPick의 인기 숙소 고도화는 서로 다른 두 문제를 순서대로 해결한 과정이다.

```text
V1 응답 캐시
→ 동일한 인기 숙소 결과를 반복 계산하는 성능 문제 해결

V2 기간별 랭킹
→ 누적 점수로 인해 최근 인기가 늦게 반영되는 최신성 문제 해결
```

응답 캐시 TTL과 랭킹 원본의 시간 범위는 서로 다른 설계 요소이며, 캐시 만료만으로
랭킹 최신성 문제를 해결할 수 없다.
