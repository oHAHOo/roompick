# 예약 대기열 시스템 도입 배경

## 1. 목적

동일 객실에 예약 요청이 동시에 몰릴 때 지금 구조가 보장하는 것과
보장하지 않는 것을 정리하고, Kafka 기반 대기열 시스템의 필요성을
실측으로 검증합니다.

---

## 2. 문제 상황

지금 예약 로직은 두 사람이 같은 방을 동시에 예약하려 하면 DB
락(lock)으로 한 명을 잠깐 대기시킵니다. 락 덕분에 같은 방이 두 번
예약되는 일은 생기지 않습니다. 이 부분은 이미 구현되어 있고 정상
동작합니다.

문제는 이 락이 "누가 먼저 요청했는가"를 보지 않는다는 점입니다.
여러 요청이 동시에 락을 두고 경쟁하면 누가 먼저 락을 잡을지는 서버
내부 스레드 처리 순서에 달려있고, 이는 사실상 무작위입니다. 즉
먼저 버튼을 누른 사람이 오히려 예약에 실패하고, 늦게 누른 사람이
방을 가져가는 일이 실제로 발생할 수 있습니다.

지금까지는 사용자들이 보통 서로 다른 방과 날짜를 예약해 동일 객실을
두고 경쟁하는 상황 자체가 드물었기 때문에 이 문제가 드러나지
않았습니다. 하지만 특정 객실을 한정 수량 특가로 내놓으면 판매
시작 순간 다수 사용자가 동일 객실을 동시에 노리는 상황을
구조적으로 만들며, 이때 위 순서 문제가 실제로 발생합니다.

---

## 3. 검증

### 3.1 실험 설계

30명이 동일한 순간에 예약을 요청하는 상황을 가정하고 두 방식을
비교했습니다.

- **A. 락 경쟁 방식(현재 구조)**: 30개 요청이 동시에 하나의 락을
  얻으려 경쟁. 요청 순번과 실제 락 획득 순번을 각각 기록.
- **B. Kafka 방식(파티션 + 단일 컨슈머)**: 30개 요청을 하나의
  파티션에 도착 순서대로 적재(append)하고, 그 파티션을 구독하는
  컨슈머 하나가 적재된 순서 그대로 하나씩 처리. Kafka 파티션은
  로그 구조라 먼저 적재된 메시지가 항상 먼저 있는 위치(오프셋)를
  갖고, 컨슈머는 오프셋이 낮은 메시지부터 순서대로 읽으므로 처리
  순서가 적재 순서와 항상 같습니다.

### 3.2 결과

| 방식 | 요청 순서와 처리 순서가 다른 비율 |
|---|---|
| A. 락 경쟁 방식(현재 구조) | 30건 중 29건 (96.7%) |
| B. Kafka 방식(파티션 + 단일 컨슈머) | 30건 중 0건 (0%) |

A 방식에서는 가장 늦게 요청한 30번째 건이 실제로는 3번째로
처리되는 등, 요청 순서와 처리 순서가 대부분 일치하지 않았습니다.
B 방식에서는 30건 전부 요청 순서와 처리 순서가 일치했습니다.

이런 차이가 나는 이유는 처리 방식 자체가 다르기 때문입니다. A
방식은 처리 시점마다 매번 다시 경쟁하므로 승자가 순전히 타이밍에
좌우됩니다. B 방식은 파티션에 적재되는 순간 순서(오프셋)가
확정되고, 컨슈머는 그 순서대로 꺼내 처리하기만 하므로 순서가
바뀔 여지가 없습니다.

### 3.3 왜 Redis가 아니라 Kafka인가

같은 문제를 Redis의 원자적 연산(`SETNX`)이나 정렬된 자료구조로도
풀 수 있습니다. 다만 Redis 방식은 "누가 먼저 락을 잡는가"를 매번
새로 경쟁시키는 구조라 순서를 별도의 자료구조(예: 대기 순번을
저장하는 정렬 자료구조)로 직접 관리해야 합니다. Kafka는 파티션
자체가 도착 순서를 기록하는 로그이기 때문에 별도의 순번 관리
없이 "적재된 순서 = 처리할 순서"가 그대로 보장됩니다. 또한 처리
결과가 브로커에 로그로 남기 때문에, 처리 중이던 서버가 죽어도
처리 못한 요청이 사라지지 않고 다시 처리할 수 있습니다.

### 3.4 실제 서비스 환산

디럭스 더블룸 1개가 한정 수량 특가로 정각에 판매 시작되는 상황을
가정하면, 현재 구조에서는 가장 먼저 요청한 사용자가 방을 받지
못하는 경우가 예외적인 상황이 아니라 위 실험 결과 기준 거의
매번(96.7%) 발생하는 일이 됩니다. 이는 버그가 아니라 현재 구조가
처리 순서를 애초에 보장하지 않기 때문에 발생하는 구조적인
결과입니다.

## 4. Kafka 기반 대기열 시스템이 추가로 보장하는 것

| | 현재 구조(락) | Kafka 기반 대기열 시스템 |
|---|---|---|
| 동일 객실 중복 예약 방지 | O | O (기존 DB 락을 그대로 최종 안전망으로 유지) |
| 요청 순서대로 우선권 부여 | X (실측 96.7% 불일치) | O (실측 100% 일치) |
| 사용자에게 대기 순번 제공 | X | O |
| 결제 미완료 이탈 시 다음 대기자에게 순서 승계 | X | O |

동일 객실 중복 예약을 막는 정합성은 이미 확보되어 있으므로, 이
시스템은 정합성을 대체하지 않고 기존 DB 락을 그대로 둔 채 그 위에
요청 순서에 대한 공정성과 대기 상태 가시성, 승계 처리를
추가합니다. Kafka는 어떤 순서로 처리할지를 결정하는 역할만
맡고, 실제 DB에 예약을 기록하는 시점의 정합성은 여전히 기존
비관적 락이 담당합니다.

## 5. 최종 구조

논의 과정에서 범위와 구조가 여러 차례 다듬어졌고, 최종 결정을
반영합니다.

**대상은 한정 수량 특가**: 이 시스템이 다루는 건 **특정 객실
하나를 한정 수량 특가로 내놓았을 때 몰리는 사람들 사이의
처리 순서를 관리하는 것**입니다. 특가 가격이 어떻게 정해지는지는
이 시스템의 관심사가 아니며, 관리자가 특가 상품을 등록하기만
하면(수량이 제한된 판매라는 조건만 성립하면) 이 문제가 발생합니다.

**특가 대상은 객실 1개 = 특가 슬롯 1개**: `Room`은 이미 물리적
객실 하나(고유한 `room_number`)를 나타내므로, 특가 판매 단위를
객실과 1:1로 묶으면 별도의 수량(재고) 필드가 필요 없습니다.
"이 객실이 특가 대상으로 등록되어 있는가"와 "이미 누가
잡았는가"만 판단하면 됩니다. 여러 객실을 동시에 특가로 내놓고
싶으면 특가 상품 행을 객실 수만큼 만들면 되고, 각 특가 상품은
서로 완전히 독립적으로 경쟁이 진행됩니다.

**신규 테이블: `special_offers`**

| 컬럼 | 설명 |
|---|---|
| id | PK |
| room_id (unique) | 특가 대상 객실 (1:1) |
| price | 특가 가격 (1박 가격) |
| starts_at / ends_at | 판매 기간 |
| check_in_date / check_out_date | 특가로 확정되는 숙박 기간 |
| status | SCHEDULED / ACTIVE / ENDED |

**입장 통제는 범위에서 제외**: 초기 설계에는 "서버가 감당 가능한
인원만큼만 배치로 실제 예약 시도를 허용"하는 1단계 입장 통제를
Kafka 순서 처리 앞에 두는 2단계 구조를 검토했습니다. 하지만 순서
보장이라는 이슈의 핵심 문제는 Kafka 단계만으로 이미 해결되고,
입장 통제가 막으려던 문제("Producer 호출 자체가 감당 안 되는
트래픽")는 실측으로 증명된 적이 없어 이번 범위에서 제외했습니다.
필요성이 실제로 확인되면 별도 이슈로 다룹니다. 최종적으로는
예약 요청 API가 점유 요청을 발행하면 곧바로 Kafka 파티션에
적재되고, 컨슈머가 오프셋 순서대로 하나씩 처리하는 단일 단계
구조입니다.

파티션 키는 `special_offers.id`(offer_id)를 사용합니다. 같은
특가 상품에 대한 요청은 항상 같은 파티션에 쌓여 순서가
보장되고, 서로 다른 특가 상품끼리는 원래 아무 관계가 없으므로
같은 파티션을 공유하지 않는 게 이상적입니다. 다만 파티션
개수가 특가 상품 수보다 적으면 서로 다른 특가끼리 파티션을
공유하게 되어 서로의 처리 순서에 영향을 줄 수 있습니다. 이
트레이드오프는 실제 운영 규모(동시에 진행되는 특가 개수)가
확인된 뒤 파티션 수를 조정하는 방식으로 다룹니다.

**대기열은 DB 테이블로 관리**: 순서와 상태를 Redis나 Kafka
내부 상태가 아니라 별도 DB 테이블로 관리합니다. Kafka delay
topic처럼 시간 지연을 이벤트로 구현하는 대신, 이미 있는 스케줄러
폴링 방식을 그대로 재사용합니다.

**신규 테이블: `waitlists`**

| id | offer_id | member | status | requested_at | hold_expires_at | reservation_id |
|---|---|---|---|---|---|---|
| 1 | 1 | 고객A | HOLD | 10:00:00 | 10:05:00 | 501 |
| 2 | 1 | 고객B | WAIT | 10:00:01 | null | null |
| 3 | 1 | 고객C | WAIT | 10:00:02 | null | null |

- `status`: `WAIT`(대기) → `HOLD`(점유 중, 결제 대기) → `CONFIRMED`(결제 완료) 또는 `EXPIRED`(만료)
- `reservation_id`: HOLD로 등록되며 함께 생성된 예약을 추적. 결제
  성공/실패 시 이 값으로 waitlist를 찾아 상태를 동기화하고, HOLD가
  만료될 때 이 예약을 명시적으로 취소한 뒤 다음 대기자를 승격한다.
- 컨슈머가 처리할 때 같은 `offer_id`로 `HOLD`/`CONFIRMED` 행이 이미 있는지 존재 여부만 확인 (수량 비교가 아니라 존재 확인)
  - 없으면 → 이번 요청을 `HOLD`로 등록
  - 있으면 → `WAIT`로 등록
- 스케줄러가 주기적으로 `HOLD`이면서 `hold_expires_at`이 지난 행을 찾아 `EXPIRED`로 바꾸고, 같은 `offer_id`의 `WAIT` 중 **`id`(자동증가) 오름차순으로 가장 앞선** 행을 `HOLD`로 승격(승계)한다.
  같은 `offer_id`의 요청은 항상 같은 Kafka 파티션에서 컨슈머 1개가
  순차 처리하므로, `id` 오름차순이 곧 실제 처리(적재) 순서와 항상
  일치한다. `requested_at`(HTTP 요청 접수 시각)은 동시 요청이
  몰리면 밀리초 단위로 동률이 생기고 스레드 스케줄링에 따라 Kafka
  적재 순서와 어긋날 수 있어 승계 기준으로 쓰지 않는다.
