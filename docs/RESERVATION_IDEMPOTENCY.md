# 예약 생성 API 멱등성 정책

## 1. 목적

예약 생성 요청이 네트워크 재시도나 중복 클릭으로 반복되어도
동일한 예약이 여러 건 생성되지 않도록 보장합니다.

이 정책은 동일 회원이 같은 요청을 재전달하는 경우를 다룹니다.
서로 다른 멱등성 키로 동일 객실을 동시에 예약하는 요청은
객실 단위 비관적 락 정책을 따릅니다.

## 2. 요청 헤더 정책

예약 생성 API는 다음 요청 헤더를 필수로 받습니다.

```http
Idempotency-Key: reservation-create-20260810-0001
```

- 헤더 이름은 `Idempotency-Key`입니다.
- 키가 누락되거나 공백으로만 구성되면
  `400 INVALID_INPUT_VALUE`를 반환합니다.
- 키는 앞뒤 공백을 제거한 값을 사용합니다.
- 정규화한 키는 1자 이상 100자 이하여야 합니다.
- 키의 유효 범위는 회원 단위입니다.
- 서로 다른 회원은 같은 키 문자열을 독립적으로 사용할 수 있습니다.

## 3. 동일 요청 판단 기준

다음 필드를 정해진 순서로 조합한 뒤 SHA-256 해시를 생성합니다.

1. 객실 ID
2. 체크인 날짜
3. 체크아웃 날짜
4. 예약 인원

정규 문자열 형식은 다음과 같습니다.

```text
roomId|checkInDate|checkOutDate|guestCount
```

날짜는 ISO-8601 `yyyy-MM-dd` 형식을 사용합니다.
JSON 필드 순서나 공백은 요청 동일성 판단에 영향을 주지 않습니다.

## 4. 처리 결과

| 조건 | 처리 결과 |
| --- | --- |
| 최초 키·요청 | 예약 생성 후 `201 Created` |
| 동일 회원·동일 키·동일 요청 | 기존 예약을 `201 Created`로 반환 |
| 동일 회원·동일 키·다른 요청 | `409 RESERVATION_IDEMPOTENCY_CONFLICT` |
| 다른 회원·동일 키 | 회원별로 독립 처리 |
| 최초 처리 트랜잭션 실패 | 멱등성 데이터도 롤백하고 재시도 허용 |

동일 요청의 모든 성공 응답은 같은 `reservationId`를 반환합니다.

## 5. 저장 및 동시성 정책

MySQL의 예약 멱등성 테이블을 기준 데이터로 사용합니다.
회원 ID와 멱등성 키 조합에는 Unique Constraint를 적용합니다.

처리 순서는 다음과 같습니다.

1. 멱등성 키와 요청 값을 검증합니다.
2. 요청 해시를 생성합니다.
3. 회원 ID와 멱등성 키를 기준으로 멱등성 행을 확보합니다.
4. 멱등성 행에 비관적 쓰기 락을 획득합니다.
5. 기존 요청 해시와 현재 요청 해시를 비교합니다.
6. 완료된 동일 요청이면 저장된 예약을 반환합니다.
7. 신규 요청이면 객실 행에 비관적 쓰기 락을 획득합니다.
8. 예약을 생성하고 멱등성 처리 상태와 예약 ID를 저장합니다.
9. 전체 트랜잭션을 커밋합니다.

락 획득 순서는 항상 다음 순서를 유지합니다.

```text
예약 멱등성 행 → 객실 행
```

멱등성 데이터 확보, 객실 락, 예약 저장 및 처리 완료는
하나의 트랜잭션에서 수행합니다. 예약 생성 중 예외가 발생하면
멱등성 데이터까지 함께 롤백되어 같은 키로 다시 요청할 수 있습니다.

## 6. 테스트 범위

### Controller 테스트

- 정상 멱등성 키가 Facade에 전달됩니다.
- 키 누락은 `400 INVALID_INPUT_VALUE`입니다.
- 빈 키는 `400 INVALID_INPUT_VALUE`입니다.
- 멱등성 충돌은 `409 RESERVATION_IDEMPOTENCY_CONFLICT`입니다.

### 단위 테스트

- 요청 해시는 네 예약 필드를 모두 반영합니다.
- 동일 입력은 항상 같은 해시를 생성합니다.
- 한 필드라도 달라지면 다른 해시를 생성합니다.
- 동일 키·동일 해시는 기존 처리 결과를 반환합니다.
- 동일 키·다른 해시는 충돌로 처리합니다.

### MySQL 통합 테스트

- 동일 요청을 순차 재전달해도 예약은 한 건만 생성됩니다.
- 동일 요청을 동시에 전달해도 예약은 한 건만 생성됩니다.
- 모든 성공 응답이 같은 `reservationId`를 반환합니다.
- 같은 키의 다른 요청은 충돌로 처리됩니다.
- 다른 회원은 같은 키를 독립적으로 사용합니다.
- 최초 트랜잭션 실패 후 같은 키로 재시도할 수 있습니다.
- 서로 다른 키의 객실 경합은 기존 예약 동시성 정책을 따릅니다.
