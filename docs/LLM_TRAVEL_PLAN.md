# LLM 여행 계획 설계

- 문서 목적: LLM을 어떻게 도입했는지, 왜 그렇게 만들었는지를 설명한다.
- 대상: LLM을 다뤄본 경험이 없어도 이 기능을 읽고 수정할 수 있어야 한다.
- 관련 문서: API 명세는 `docs/API_SPEC_TRAVELPLAN.md`, 테이블은 `docs/ERD.md` 6-3절

---

## 1. 알아야 할 용어

| 용어 | 의미 |
| --- | --- |
| LLM | 텍스트를 입력받아 텍스트를 생성하는 모델. 이 프로젝트는 Anthropic의 Claude를 사용한다. |
| 토큰 | 모델이 텍스트를 처리하는 최소 단위. 한국어는 글자 하나가 토큰 한 개 이상이 될 수 있다. 요금은 토큰 수로 계산한다. |
| 입력 토큰 / 출력 토큰 | 모델에 보낸 텍스트의 토큰 수 / 모델이 생성한 텍스트의 토큰 수. 출력 토큰 단가가 더 높다. |
| 프롬프트 | 모델에 보내는 지시문. 이 기능에서는 "JSON으로만 답하라" 같은 규칙을 담는다. |
| thinking | 모델이 답을 내기 전에 내부적으로 추론하는 과정. 이 추론도 출력 토큰으로 과금된다. |
| 환각(hallucination) | 모델이 사실이 아닌 내용을 그럴듯하게 생성하는 현상. 이 기능에서는 등록되지 않은 숙소를 추천하는 형태로 나타날 수 있다. |

## 2. 기능이 하는 일

사용자가 **좌표·숙박 기간·인원**을 보내면 두 가지를 돌려준다.

1. 날짜 수에 맞는 **여행 일정** (1일차, 2일차 형태로 활동 목록 포함)
2. 그 일정에 맞는 **숙소 추천** (RoomPick에 등록된 숙소 중에서만)

엔드포인트는 `POST /api/v1/travel-plans`이고 로그인이 필요 없다.

좌표를 직접 받는 이유는 기존 장소 검색 API(`GET /api/v1/places/search`)가 이미 장소명을 좌표로
바꿔주기 때문이다. 프론트는 장소 검색으로 좌표를 먼저 얻고 그 값을 이 API에 넘긴다. 이 API가
장소명을 다시 해석하지 않으므로 Kakao API를 중복 호출하지 않는다.

---

## 3. LLM이 하는 일과 하지 않는 일

이 구분이 이 설계의 핵심이다.

**LLM이 하는 일**

- 여행 일정 텍스트 생성 (`summary`, `activities`)
- 주어진 숙소 후보 중 어느 것이 일정에 맞는지 **선택**
- 선택한 이유 텍스트 생성 (`reason`)

**LLM이 하지 않는 일**

- 숙소를 검색하거나 목록을 만드는 일. 후보 목록은 서버가 DB에서 조회해 전달한다.
- 숙소의 이름·주소·거리를 정하는 일. 이 값들은 응답에 담길 때 DB 조회 결과에서 채운다.
- 가격·편의시설·평점 판단. 이 정보는 아예 전달하지 않는다.

즉 **LLM은 "무엇을 추천할지" 고르기만 하고, "추천된 것이 무엇인지"는 DB가 결정한다.**

## 4. 전체 흐름

호출 방향은 프로젝트 규칙과 동일하게 `Controller → Facade → Service`다.

```
POST /api/v1/travel-plans
  │
  ├─ 1. TravelPlanController        요청 수신
  ├─ 2. TravelPlanFacade            Service로 위임
  └─ 3. TravelPlanService.generatePlan()
         │
         ├─ 3-1. 입력 검증
         │        좌표 범위, 날짜 순서, 과거 날짜, 최대 14박, 인원 1명 이상
         │        → 실패하면 여기서 400. LLM을 호출하지 않는다.
         │
         ├─ 3-2. 숙소 후보 조회
         │        AccommodationLocationSearchService.searchNearby()
         │        반경 10km 안의 ACTIVE 숙소 최대 5개
         │
         ├─ 3-3. LLM 호출
         │        TravelPlanLlmClient.generate()
         │        후보 목록에 0, 1, 2... 인덱스를 붙여 프롬프트에 포함
         │        → 일정 + 선택된 인덱스 + 이유 + 토큰 사용량을 받는다
         │
         ├─ 3-4. 인덱스를 실제 숙소와 매핑
         │        3-2에서 이미 조회해둔 DTO에서 이름·주소·거리·이미지를 가져온다
         │
         ├─ 3-5. 감사 로그 저장
         │        AiUsageLogService.save()  — 토큰 수, 소요 시간, 요청 규모
         │
         └─ 3-6. 응답 반환
```

### 패키지 구조

```
domain/travelplan/
├── controller/TravelPlanController        엔드포인트
├── facade/TravelPlanFacade                위임
├── service/
│   ├── TravelPlanService                  검증·조율·매핑
│   └── AiUsageLogService                  감사 로그 저장 (트랜잭션)
├── client/
│   ├── TravelPlanLlmClient                인터페이스
│   └── anthropic/ClaudeTravelPlanClient   Claude 구현체
├── model/                                 제공자 중립 모델
│   ├── TravelPlanLlmRequest
│   ├── TravelPlanLlmResult                일정 + 선택 + 토큰 사용량
│   └── TravelPlanCandidate                LLM에 넘기는 숙소 후보
├── entity/AiUsageLog
├── repository/AiUsageLogRepository
└── dto/                                   요청·응답 DTO

global/config/travelplan/
├── AnthropicClientConfig                  SDK 클라이언트 빈
└── TravelPlanLlmProperties                모델·키·타임아웃 설정
```

## 5. 설계 결정과 이유

### 5-1. 추천을 숙소 이름이 아니라 인덱스로 받는다

**결정**: 프롬프트에 후보를 `candidateIndex 0`, `candidateIndex 1`처럼 번호를 붙여 전달하고,
LLM은 번호만 반환한다.

**이유**: LLM에게 숙소명을 자유롭게 쓰게 하면 등록되지 않은 숙소를 생성할 수 있다. 번호로만 받으면
선택할 수 있는 범위가 후보 목록으로 제한된다. 범위를 벗어난 번호는 버리면 되므로, 모델이 잘못된
값을 내도 응답에 반영되지 않는다.

**대안과 트레이드오프**: 숙소 ID를 직접 받는 방법도 있다. 다만 ID는 값의 범위가 넓어 존재하지 않는
ID를 만들어낼 여지가 있고, 검증하려면 DB를 다시 조회해야 한다. 0부터 시작하는 작은 인덱스는
길이 비교만으로 검증이 끝난다.

### 5-2. 응답의 사실 정보는 DB에서 채운다

**결정**: `accommodationId`, `name`, `address`, `distanceKm`, `imageUrl`은 3-2에서 조회한 DTO에서
가져온다. LLM이 생성한 텍스트는 `itinerary`와 `reason`뿐이다.

**이유**: LLM이 후보 목록을 그대로 반복하지 않고 이름을 살짝 바꿔 쓰거나 주소를 잘못 옮길 수 있다.
사실 정보를 DB에서만 가져오면 그런 오류가 사용자에게 도달하지 않는다.

### 5-3. LLM 호출을 DB 트랜잭션 밖에서 한다

**결정**: `TravelPlanService.generatePlan()`에는 `@Transactional`을 붙이지 않는다. 저장만
`AiUsageLogService.save()`에서 트랜잭션을 연다.

**이유**: LLM 호출은 실측 13~17초가 걸린다. 트랜잭션 안에서 호출하면 그 시간 동안 DB 커넥션을
점유한다. 동시 요청이 늘어나면 커넥션 풀이 고갈되어 이 기능과 무관한 API까지 함께 느려진다.
기존 Kakao 장소 검색에서도 같은 원칙을 쓰고 있다(`docs/policy/ACCOMMODATION_POLICY.md` 4절).

후보 조회(`searchNearby`)는 `@Transactional(readOnly = true)`이지만 짧게 끝나고 LLM 호출 전에
종료된다.

### 5-4. LLM SDK를 Client 인터페이스 뒤에 둔다

**결정**: `TravelPlanLlmClient` 인터페이스를 두고 `ClaudeTravelPlanClient`가 구현한다. Anthropic
SDK 타입은 구현체 안에서만 쓴다.

**이유**: 두 가지다. 첫째, Service가 특정 LLM 제공자에 묶이지 않는다. 둘째, 테스트에서 이 인터페이스를
대역으로 바꾸면 실제 API를 호출하지 않고 검증할 수 있다. 기존 `PlaceSearchClient`(Kakao)와 같은 구조다.

### 5-5. 입력 검증을 LLM 호출 전에 끝낸다

**결정**: 좌표 범위, 날짜 순서, 과거 날짜, 14박 초과, 인원 등을 3-1에서 모두 검증한다.

**이유**: 호출마다 요금이 발생한다. 잘못된 요청으로 과금되지 않도록 차단한다. 14박 상한은 일정이
길어질수록 출력 토큰이 늘어나므로 비용 상한 역할도 한다.

### 5-6. 생성 결과를 저장하지 않고 감사 로그만 남긴다

**결정**: `ai_usage_logs`에 모델명·토큰 수·소요 시간·요청 규모만 저장한다. 일정 내용, 추천 이유,
추천된 숙소 ID, 요청 좌표는 저장하지 않는다.

**이유**: 초기에는 생성 내용을 모두 저장했으나 읽는 코드가 없었다. 공개 API라 회원과 연결할 수 없어
사용자 이력으로 발전할 경로도 없었다. 반면 요금이 발생하는 기능인데 토큰 수를 남기지 않아 실제
비용을 알 수 없었다. 그래서 저장 대상을 비용 관리에 필요한 값으로 바꿨다.

익명 사용자의 여행 내용을 보관 기간 정책 없이 저장하지 않게 된 것도 이유다.

**트레이드오프**: 같은 요청을 다시 보내면 다른 일정이 생성되고, 지난 계획을 다시 조회할 수 없다.
사용자 이력 기능이 필요해지면 인증을 붙이고 별도 테이블을 추가해야 한다.

## 6. 프롬프트 설계

시스템 프롬프트는 `ClaudeTravelPlanClient.SYSTEM_PROMPT`에 있다. 규칙마다 목적이 다르다.

| 규칙 | 목적 |
| --- | --- |
| JSON 객체 하나만 출력, 설명 문장 금지 | 파싱 실패를 줄인다 |
| JSON 구조를 예시로 제시 | 필드명이 달라지는 것을 막는다 |
| 숙박일 수만큼 일정 생성 | 날짜와 일정 수가 어긋나는 것을 막는다 |
| 제시된 `candidateIndex`만 사용 | 등록되지 않은 숙소 추천을 막는다 |
| 후보가 없으면 빈 배열 | 후보 0건일 때 억지로 추천하는 것을 막는다 |
| 주어진 정보만 근거로 이유 작성 | 가격·편의시설·평점을 추측하는 것을 막는다 |

사용자 메시지에는 좌표, 체크인·체크아웃, 숙박일 수, 인원, 그리고 후보 목록(인덱스·이름·주소·거리)을
담는다. 가격과 편의시설은 전달하지 않는다. 전달하지 않은 정보는 추측할 여지도 줄어든다.

## 7. 응답을 믿지 않는 장치

LLM 응답은 형식이 어긋날 수 있다고 전제하고 처리한다.

1. **코드 블록 제거**: JSON만 출력하라고 지시해도 ```` ```json ````으로 감싸 오는 경우가 있다.
   첫 `{`부터 마지막 `}`까지만 잘라내어 파싱한다.
2. **필수 필드 확인**: `itinerary`가 없으면 오류로 처리한다.
3. **일정 항목 필터링**: `day`가 없는 항목은 버린다. `activities`가 없으면 빈 목록으로 둔다.
4. **인덱스 범위 검증 이중화**: Client(`isSelectableIndex`)와 Service(`toRecommendations`)에서
   각각 범위를 확인한다. Service에서 한 번 더 하는 이유는, 범위를 벗어난 인덱스로 목록에 접근하면
   사용자에게 500 오류가 나가기 때문이다. 방어 위치가 하나뿐이면 이후 수정에서 쉽게 깨진다.

## 8. 오류 처리

| HTTP | Error Code | 조건 |
| --- | --- | --- |
| `400` | `INVALID_INPUT_VALUE` | 좌표 범위, 날짜, 14박 초과, 인원 등 입력 오류 |
| `504` | `TRAVEL_PLAN_LLM_TIMEOUT` | LLM 응답 시간 초과 |
| `503` | `TRAVEL_PLAN_LLM_RATE_LIMITED` | LLM 요청 제한(429) |
| `503` | `TRAVEL_PLAN_LLM_UNAVAILABLE` | 인증 실패를 포함한 LLM 서비스 오류 |
| `502` | `TRAVEL_PLAN_LLM_INVALID_RESPONSE` | JSON이 아님, `itinerary` 누락, 빈 응답 |

외부 API 오류를 그대로 노출하지 않고 프로젝트 오류 코드로 변환한다. 기존 `PLACE_API_*`와 같은 방식이다.

## 9. 비용

| 항목 | 값 |
| --- | --- |
| 모델 | `claude-opus-5` |
| 단가 | 입력 1M 토큰당 $5, 출력 1M 토큰당 $25 |
| 실측 사용량 | 입력 893 토큰, 출력 634 토큰 (2박 2인, 후보 5개) |
| 실측 호출 1건 비용 | 약 $0.02 |
| 실측 소요 시간 | 13~17초 |

출력 토큰에는 thinking 토큰이 포함된다.

### 비용을 통제하는 장치

- 입력 검증을 LLM 호출 전에 끝낸다.
- 후보를 최대 5개로 제한해 입력 토큰을 제한한다.
- 최대 14박으로 제한해 출력 토큰을 제한한다.
- 프론트는 응답이 오기 전 버튼을 비활성화해 중복 제출을 막는다.
- `ai_usage_logs`로 실제 사용량을 집계한다.

`ANTHROPIC_MODEL` 환경변수로 더 저렴한 모델로 교체할 수 있다.

**아직 없는 장치**: 요청 수 제한이 없다. 로그인 없이 호출할 수 있고 호출마다 과금되므로, 공개 노출
전에 reverse proxy나 API Gateway 계층에서 제한을 두는 것을 우선 검토해야 한다.

## 10. 설정

| 환경변수 | 필수 | 기본값 | 설명 |
| --- | --- | --- | --- |
| `ANTHROPIC_API_KEY` | 필수 | 없음 | 없으면 애플리케이션이 기동하지 않는다 |
| `ANTHROPIC_MODEL` | 선택 | `claude-opus-5` | 사용할 모델 |

등록되어 있어야 동작한다.

로컬 실행 방법과 키가 없을 때의 동작은 `frontend/README.md`에 있다.

## 11. 테스트 방법

| 테스트 | 검증 대상 |
| --- | --- |
| `TravelPlanServiceTest` | 입력 검증, 인덱스 매핑, 후보 0건 처리, 감사 로그 저장 |
| `ClaudeTravelPlanClientTest` | JSON 파싱, 코드 블록 제거, 범위 밖 인덱스 제거, 토큰 추출, 오류 변환 |
| `TravelPlanFacadeTest` | Service 위임 |

모든 테스트는 SDK 클라이언트를 대역으로 대체해 실제 API를 호출하지 않는다. 실제 Anthropic API를
호출하는 자동 테스트는 만들지 않았다. 요금이 발생하고 외부 서비스 상태에 따라 CI가 불안정해진다.

실제 호출 확인은 로컬에서 수동으로 한다.

| 요청 수 제한 없음 | 로그인 없이 호출 가능하고 매번 과금된다. 운영 노출 전 필요하다. |
| 추천 중복 미제거 | LLM이 같은 인덱스를 두 번 반환하면 같은 숙소가 두 번 추천된다. 범위 검증만 하고 중복은 걸러내지 않는다. |
| 스키마 강제 아님 | 프롬프트 지시와 문자열 파싱에 의존한다. Anthropic API의 구조화 출력 기능으로 바꾸면 형식 오류를 원천 차단할 수 있다. |
| 재시도 없음 | 형식 오류 시 재시도하지 않고 `502`로 실패한다. |
| 일정 내용 미검증 | 일정에 포함된 장소명, 운영시간, 이동 시간은 검증하지 않은 LLM 생성 텍스트다. |
| 예약 가능 여부 미반영 | 추천된 숙소가 해당 날짜에 만실일 수 있다. 날짜 기준 예약 가능 여부를 필터링하지 않는다. |
| 실패율 알 수 없음 | 호출 실패 시 저장 전에 예외가 발생하므로 감사 로그에는 성공한 호출만 남는다. |
| 도메인 담당자 미정 | `travelplan`은 기존 담당 구분(숙소·객실·예약 / 결제·관리자 / 회원·인증·보안)에 속하지 않는다. |
