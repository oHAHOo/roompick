## 1. 프로젝트 기본 정보

- 프로젝트명: **RoomPick(룸픽)**
- 서비스 유형: **숙박 예약 애플리케이션**
- 개발 방식: 가장 작은 MVP를 먼저 배포한 뒤 기능을 버전별로 추가한다.
- 핵심 거래: 사용자가 객실의 예약 가능 여부를 확인하고 예약·결제·취소하는 과정

### 담당 영역

- IMSUN9: 숙소, 객실, 예약, 전체 통합
- minjae123123: 결제, 관리자 기능
- oHAHOo: 회원, 인증·인가, 보안

관리자 숙소·객실 등록은 minjae123123이 유스케이스를 담당하며 IMSUN9이 소유한 숙소·객실 도메인 Service를 사용한다. `ADMIN` 권한과 접근 제어는 oHAHOo가 담당한다.

### 한 줄 소개

> RoomPick은 관리자가 숙소와 객실을 등록·공개하고, 회원이 공개된 객실의 정보를 확인해 원하는 숙박 날짜를 예약할 수 있는 숙박 예약 서비스다.

현재 MVP의 목적은 여러 숙소를 탐색하는 플랫폼을 만드는 것이 아니라, **관리자 등록부터 객실 하나의 예약 거래까지 정상적으로 동작하는지 검증하는 것**이다.

## 2. 현재 팀에서 확정한 MVP 원칙

1. 기능을 최대한 작게 시작한다.
2. 관리자가 숙소와 실제 객실을 등록할 수 있다.
3. 숙소는 등록 시 `ACTIVE`, 객실은 등록 시 `INACTIVE`로 시작한다.
4. 관리자가 객실을 공개하면 객실이 `ACTIVE`로 전환된다.
5. `INACTIVE` 객실은 사용자 화면에 노출하지 않는다.
6. `SOLD_OUT`은 객실 DB 상태가 아니라 사용자가 선택한 날짜의 예약 존재 여부로 계산한다.
7. 초기 MVP에서는 숙소 목록과 검색 기능을 제외했으며, 현재 브랜치에는 후속 확장으로 숙소 목록·장소 후보 검색·좌표 기반 주변 숙소 검색이 구현되어 있다.
8. MVP 검증에는 관리자가 등록한 숙소 1개와 실제 객실 1개를 사용한다.
9. 사용자는 전달받은 ID로 공개된 숙소·객실 상세 화면에 진입한다.
10. 초기 MVP에서는 관리자 숙소·객실 삭제를 제외했으며, 현재 브랜치에는 후속 확장으로 `INACTIVE` 상태 기반 논리 삭제가 구현되어 있다.
11. MVP에서는 객실 1개에 대한 예약·결제·취소 흐름을 우선 검증한다.
12. 추가 기능은 MVP 배포 후 별도의 버전으로 구분하여 개발한다.
13. 기능 범위는 작게 유지하되, 상태와 계층 구조는 이후 확장할 수 있도록 설계한다.

## 3. MVP 목표

> 관리자가 숙소와 객실을 등록하고 객실을 공개한 뒤, 회원이 공개된 객실의 상세 정보를 확인해 체크인·체크아웃 날짜를 선택하고 예약·결제·조회·취소할 수 있다.

### MVP 완료 조건

- 회원이 로그인할 수 있다.
- 일반 회원가입으로 관리자 권한을 획득할 수 없다.
- 관리자만 숙소와 객실을 등록할 수 있다.
- 객실 등록 직후 상태는 `INACTIVE`이다.
- 관리자가 객실을 공개하면 `ACTIVE`로 변경된다.
- 비관리자의 등록·상태 변경 요청은 거절된다.
- `INACTIVE` 객실은 사용자용 조회에서 노출되지 않는다.
- 공개된 숙소와 객실의 상세 정보를 조회할 수 있다.
- 선택한 숙박 기간에 객실을 예약할 수 있는지 확인할 수 있다.
- 선택한 기간에 활성 예약이 존재하면 화면에서 `SOLD_OUT`으로 표시할 수 있다.
- 예약 가능한 경우 예약과 간단한 결제를 진행할 수 있다.
- 결제 성공 시 예약이 확정된다.
- 결제 실패 시 예약이 확정되지 않고 해당 기간의 객실 점유가 해제된다.
- 회원이 자신의 예약을 조회할 수 있다.
- 취소 가능한 예약을 취소하면 해당 기간이 다시 예약 가능해진다.
- 핵심 예약 흐름에 대한 테스트가 통과한다.
- 외부에서 접근할 수 있는 개발 서버에 배포된다.

## 4. MVP 사용자 흐름

```text
관리자 로그인
→ 숙소 등록
→ 등록된 숙소에 실제 객실 등록(INACTIVE)
→ 객실 공개(ACTIVE)
→ 회원가입·로그인
→ 공개된 객실 상세 조회
→ 체크인·체크아웃 날짜 선택
→ 예약 가능 여부 확인
→ 예약 가능하면 ACTIVE, 이미 예약됐으면 SOLD_OUT 표시
→ 예약 생성 및 해당 기간 점유
→ 간단한 결제 진행
→ 결제 성공 시 예약 확정
→ 내 예약 조회
→ 예약 취소 및 해당 기간 점유 해제
```

### 결제 실패 흐름

```text
예약 생성 및 해당 기간 점유
→ 결제 실패
→ 예약 미확정 처리
→ 해당 기간 점유 해제
→ 이후 예약 가능 여부 조회에서 다시 ACTIVE로 계산 가능
```

객실 DB 상태를 `SOLD_OUT`으로 바꾸거나 결제 실패 시 `ACTIVE`로 복구하는 방식은 사용하지 않는다.

### 현재 구현된 탐색 확장 흐름

```text
장소명 입력
→ 공개 장소 검색 API
→ Kakao Local API 장소 후보와 latitude / longitude 반환
→ 사용자가 후보 선택
→ 선택한 좌표로 주변 숙소 검색
→ MySQL Bounding Box 또는 Elasticsearch 결과 반환
```

장소 후보 검색과 숙소 위치 검색은 분리된 요청이다. 후보를 선택하기 전에는 숙소 DB나 Elasticsearch를
조회하지 않으며, Kakao 외부 API 호출 중 DB 트랜잭션을 시작하지 않는다.

## 5. MVP 구현 범위

### 회원

- 회원가입
- 로그인
- 인증된 회원 식별
- 회원 권한 `USER`, `ADMIN` 구분
- 관리자 전용 API 접근 제어
- 일반 회원가입의 기본 권한은 `USER`이며 요청으로 `ADMIN`을 선택할 수 없음

### 숙소·객실

- 관리자 숙소 등록
- 관리자 객실 등록
- 객실 등록 기본 상태 `INACTIVE`
- 관리자 객실 공개·비공개 상태 전환의 최소 기능
- 공개된 숙소·객실 상세 조회
- `INACTIVE` 객실 사용자 조회 제외
- 체크인·체크아웃 날짜 기준 예약 가능 여부 확인
- 선택 날짜 기준 `ACTIVE`·`SOLD_OUT` 표시 상태 계산

### 현재 구현된 탐색 확장

- 비로그인 사용자의 장소명 기반 후보 장소 검색
- Kakao Local API 응답의 장소 후보와 위도·경도 반환
- 선택한 좌표 기준 주변 `ACTIVE` 숙소 검색
- MySQL Bounding Box와 Elasticsearch 위치 검색 엔진 선택

### 예약

- 예약 생성
- 내 예약 단건 또는 목록 조회
- 예약 취소
- 동일 객실의 겹치는 날짜에 대한 기본 중복 예약 검증
- 만료 전 `PENDING_PAYMENT`와 `CONFIRMED` 예약만 해당 기간의 예약 가능 여부를 막음
- `CANCELED`, `EXPIRED`, `COMPLETED` 예약은 신규 예약을 막지 않음

### 결제

- 결제 준비
- 결제 성공 처리
- 결제 실패 처리
- 결제 실패 시 예약 상태 변경을 통한 해당 기간 점유 해제

MVP에서는 실제 PG 연동 대신 테스트 가능한 간단한 결제 구현을 사용할 수 있다. 단, 실제 PG로 교체할 가능성을 고려해 결제 연동부를 인터페이스로 분리하는 방식을 권장한다.

### 테스트·배포

- 관리자 숙소·객실 등록 성공 테스트
- 객실 등록 시 `INACTIVE` 생성 테스트
- 객실 공개 시 `ACTIVE` 전환 테스트
- 일반 회원의 관리자 등록·상태 변경 API 접근 거절 테스트
- 같은 숙소의 객실 번호 중복 등록 거절 테스트
- `INACTIVE` 객실 사용자 조회 제외 테스트
- 예약 가능 날짜 검증 테스트
- 날짜가 겹치는 예약 존재 시 `SOLD_OUT` 계산 테스트
- 중복 예약 거절 테스트
- 결제 성공 시 예약 확정 테스트
- 결제 실패 시 해당 기간 점유 해제 테스트
- 예약 취소 시 해당 기간 점유 해제 테스트
- CI에서 테스트 자동 실행
- 1차 개발 서버 배포

## 6. MVP에서 명시적으로 제외하는 기능

다음 기능은 초기 MVP 제안에 포함하지 않았다. 이 중 숙소 목록, 장소 후보 검색과 좌표 기반 주변 숙소
검색은 이후 확장으로 구현되었으며, 아래 나머지 기능은 별도 요청이나 팀 합의 없이 추가하면 안 된다.

- 객실 검색

- 객실 유형별 수량 재고와 여러 객실 일괄 등록

- 별도의 관리자 관리 화면과 대시보드
- 관리자가 객실을 `SOLD_OUT`으로 직접 변경하는 기능
- `SOLD_OUT`을 `rooms.status` 또는 `RoomStatus` Enum에 저장하는 구조
- 여러 객실을 한 번에 예약하는 기능
- 찜
- 쿠폰·포인트
- 리뷰·평점
- 지도 화면에서의 직접 영역 검색
- 자동완성, 초성 검색, 오타 보정, 동의어, 추천 검색어, 한국어 고급 분석기와 검색 랭킹 고도화
- Kakao 외 장소 검색 Provider
- 채팅·알림
- 실제 PG 결제 연동
- 부분 취소·부분 환불
- 복잡한 취소 수수료 정책
- 인기 숙소 캐싱
- 동적 가격 정책

## 7. 관리자 등록 데이터 예시

아래 값은 관리자 등록 API를 검증하기 위한 예시이며 팀 합의에 따라 변경할 수 있다.

### 숙소

- 이름: 룸픽 호텔
- 주소: 서울특별시
- 설명: RoomPick MVP 예약 테스트를 위한 숙소
- 생성 상태: `ACTIVE`

### 객실

- 이름: 디럭스 더블룸
- 기준 인원: 2명
- 최대 인원: 2명
- 1박 가격: 100,000원
- 실제 객실 수량: 1개
- 생성 상태: `INACTIVE`

숙소와 객실은 관리자 등록 API를 통해 생성한다. 객실은 공개 처리 후 `ACTIVE`가 되어야 사용자 화면에 노출된다. 일반 회원가입 요청은 권한 필드를 받지 않으며, 최초 관리자 계정 준비 방법은 회원·인증 담당 정책에 따른다. 실제 비밀번호나 토큰은 코드와 마이그레이션에 커밋하지 않는다.

## 8. 최소 비즈니스 규칙

코드에 반영되어 실제로 동작하는 규칙과 역할별 접근 권한은 기능별 `docs/policy/`에서 코드 기준으로 관리한다. 이 절과 내용이 달라지면 `docs/policy/`를 기준으로 삼는다.

### 관리자 등록·객실 공개

- 숙소·객실 등록 및 객실 상태 변경 API는 인증된 `ADMIN`만 호출할 수 있다.
- 비로그인 요청은 `401 Unauthorized`, 일반 회원 요청은 `403 Forbidden`으로 처리한다.
- 숙소 등록 시 상태는 `ACTIVE`로 시작한다.
- 객실 등록 시 상태는 `INACTIVE`로 시작한다.
- 객실은 존재하는 숙소에만 등록할 수 있다.
- 같은 숙소 안에서 실제 객실 번호는 중복될 수 없다.
- 객실 등록 시 가격은 0원 이상이고 기준 인원은 1명 이상이며 최대 인원은 기준 인원 이상이어야 한다.
- 관리자가 객실을 공개하면 `ACTIVE`, 운영을 중지하면 `INACTIVE`로 변경한다.
- 관리자가 `SOLD_OUT` 상태로 직접 변경하지 않는다.

### 객실 표시 상태

- `INACTIVE` 객실은 사용자 화면에 노출하지 않는다.
- `ACTIVE` 객실 중 선택한 숙박 기간에 활성 예약이 없으면 예약 가능 상태로 표시한다.
- `ACTIVE` 객실 중 선택한 숙박 기간에 활성 예약이 있으면 `SOLD_OUT`으로 표시한다.
- `SOLD_OUT`은 DB에 저장하지 않고 조회 시 계산한다.
- 예약 취소·결제 실패·결제 대기 만료 시 객실 상태를 직접 복구하지 않고 예약 데이터를 기준으로 다시 계산한다.

### 날짜

- 체크인 날짜는 체크아웃 날짜보다 이전이어야 한다.
- 과거 날짜는 예약할 수 없다.
- 체크아웃 날짜는 숙박일에 포함하지 않는다.
- 기존 확정 예약과 하루라도 겹치면 동일 객실을 예약할 수 없다.
- 날짜 겹침 조건은 `기존 체크인 < 요청 체크아웃 AND 기존 체크아웃 > 요청 체크인`이다.

### 인원

- 예약 인원은 1명 이상이어야 한다.
