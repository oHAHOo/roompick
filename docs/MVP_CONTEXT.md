# RoomPick MVP 기획 초안 및 AI 공유 컨텍스트

- 문서 버전: `v0.2`
- 작성일: 2026-07-21
- 최종 수정일: 2026-07-22
- 문서 목적: 팀원과 각 팀원이 사용하는 AI가 RoomPick의 현재 MVP 범위를 동일하게 이해하도록 기준을 제공한다.
- 문서 상태: 팀 회의용 초안이며, 팀 합의 후 수정될 수 있다.

## 1. 프로젝트 기본 정보

- 프로젝트명: **RoomPick(룸픽)**
- 서비스 유형: **숙박 예약 애플리케이션**
- 개발 방식: 가장 작은 MVP를 먼저 배포한 뒤 기능을 버전별로 추가한다.
- 핵심 거래: 사용자가 객실의 예약 가능 여부를 확인하고 예약·결제·취소하는 과정

### 담당 영역

- IMSUN9: 숙소, 객실, 예약, 전체 통합
- minjae123123: 결제, 관리자 기능
- oHAHOo: 회원, 인증·인가, 보안

관리자 숙소·객실 등록은 minjae123123이 유스케이스를 담당하며 IMSUN9이 소유한 숙소·객실 도메인 Service를 사용한다. `ADMIN` 권한과 접근 제어는 oHAHOo가 담당한다.

### 한 줄 소개

> RoomPick은 관리자가 숙소와 객실을 등록하고, 회원이 등록된 객실의 정보를 확인해 원하는 숙박 날짜를 예약할 수 있는 숙박 예약 서비스다.

현재 MVP의 목적은 여러 숙소를 탐색하는 플랫폼을 만드는 것이 아니라, **관리자 등록부터 객실 하나의 예약 거래까지 정상적으로 동작하는지 검증하는 것**이다.

---

## 2. 현재 팀에서 확정한 MVP 원칙

1. 기능을 최대한 작게 시작한다.
2. 관리자가 숙소와 실제 객실을 등록할 수 있다.
3. 숙소 목록과 검색 기능은 MVP에서 구현하지 않는다.
4. MVP 검증에는 관리자가 등록한 숙소 1개와 실제 객실 1개를 사용한다.
5. 사용자는 전달받은 ID로 등록된 숙소·객실 상세 화면에 진입한다.
6. 관리자 기능은 숙소·객실 등록까지만 구현하고 수정·삭제·별도 관리 화면은 제외한다.
7. MVP에서는 객실 1개에 대한 예약·결제·취소 흐름을 우선 검증한다.
8. 추가 기능은 MVP 배포 후 별도의 버전으로 구분하여 개발한다.
9. 기능 범위는 작게 유지하되, 상태와 계층 구조는 이후 확장할 수 있도록 설계한다.

## 3. MVP 목표

> 관리자가 숙소와 객실을 등록하고, 회원이 등록된 객실의 상세 정보를 확인해 체크인·체크아웃 날짜를 선택한 뒤 예약·결제·조회·취소할 수 있다.

### MVP 완료 조건

- 회원이 로그인할 수 있다.
- 일반 회원가입으로 관리자 권한을 획득할 수 없다.
- 관리자만 숙소와 객실을 등록할 수 있다.
- 비관리자의 등록 요청은 거절된다.
- 등록된 숙소와 객실의 상세 정보를 조회할 수 있다.
- 선택한 숙박 기간에 객실을 예약할 수 있는지 확인할 수 있다.
- 예약 가능한 경우 예약과 간단한 결제를 진행할 수 있다.
- 결제 성공 시 예약이 확정된다.
- 결제 실패 시 예약이 확정되지 않고 점유한 객실이 복구된다.
- 회원이 자신의 예약을 조회할 수 있다.
- 취소 가능한 예약을 취소하면 객실이 다시 예약 가능해진다.
- 핵심 예약 흐름에 대한 테스트가 통과한다.
- 외부에서 접근할 수 있는 개발 서버에 배포된다.

## 4. MVP 사용자 흐름

```text
관리자 로그인
→ 숙소 등록
→ 등록된 숙소에 실제 객실 등록
→ 회원가입·로그인
→ 등록된 객실 상세 조회
→ 체크인·체크아웃 날짜 선택
→ 예약 가능 여부 확인
→ 예약 생성 및 객실 점유
→ 간단한 결제 진행
→ 결제 성공 시 예약 확정
→ 내 예약 조회
→ 예약 취소 및 객실 복구
```

### 결제 실패 흐름

```text
예약 생성 및 객실 점유
→ 결제 실패
→ 예약 미확정 처리
→ 점유한 객실 복구
```

## 5. MVP 구현 범위

### 회원

- 회원가입
- 로그인
- 인증된 회원 식별
- 회원 권한 `USER`, `ADMIN` 구분
- 관리자 전용 API 접근 제어
- 일반 회원가입의 기본 권한은 `USER`이며 요청으로 `ADMIN`을 선택할 수 없음

### 숙소·객실

- 관리자 숙소 등록
- 관리자 객실 등록
- 등록된 숙소·객실 상세 조회
- 체크인·체크아웃 날짜 기준 예약 가능 여부 확인

### 예약

- 예약 생성
- 내 예약 단건 또는 목록 조회
- 예약 취소
- 동일 객실의 겹치는 날짜에 대한 기본 중복 예약 검증

### 결제

- 결제 준비
- 결제 성공 처리
- 결제 실패 처리
- 결제 실패 시 객실 복구

MVP에서는 실제 PG 연동 대신 테스트 가능한 간단한 결제 구현을 사용할 수 있다. 단, 실제 PG로 교체할 가능성을 고려해 결제 연동부를 인터페이스로 분리하는 방식을 권장한다.

### 테스트·배포

- 관리자 숙소·객실 등록 성공 테스트
- 일반 회원의 관리자 등록 API 접근 거절 테스트
- 같은 숙소의 객실 번호 중복 등록 거절 테스트
- 예약 가능 날짜 검증 테스트
- 중복 예약 거절 테스트
- 결제 성공 시 예약 확정 테스트
- 결제 실패 시 객실 복구 테스트
- 예약 취소 시 객실 복구 테스트
- CI에서 테스트 자동 실행
- 1차 개발 서버 배포

아래 값은 관리자 등록 API를 검증하기 위한 예시이며 팀 합의에 따라 변경할 수 있다.

### 숙소

- 이름: 룸픽 호텔
- 주소: 서울특별시
- 설명: RoomPick MVP 예약 테스트를 위한 숙소

- 이름: 디럭스 더블룸

- 1박 가격: 100,000원

## 8. 최소 비즈니스 규칙 초안

### 관리자 등록

- 숙소·객실 등록 API는 인증된 `ADMIN`만 호출할 수 있다.
- 비로그인 요청은 `401 Unauthorized`, 일반 회원 요청은 `403 Forbidden`으로 처리한다.
- 숙소 등록 시 상태는 `ACTIVE`로 시작한다.
- 객실은 존재하는 숙소에만 등록할 수 있다.
- 같은 숙소 안에서 실제 객실 번호는 중복될 수 없다.
- 객실 등록 시 가격은 0원 이상이고 기준 인원은 1명 이상이며 최대 인원은 기준 인원 이상이어야 한다.

### 날짜

- 체크인 날짜는 체크아웃 날짜보다 이전이어야 한다.
- 과거 날짜는 예약할 수 없다.
- 체크아웃 날짜는 숙박일에 포함하지 않는다.
- 기존 확정 예약과 하루라도 겹치면 동일 객실을 예약할 수 없다.

### 인원

- 예약 인원은 1명 이상이어야 한다.
- 객실 최대 인원을 초과할 수 없다.

### 예약

- 인증된 회원만 예약할 수 있다.
- 회원은 자신이 생성한 예약만 조회하거나 취소할 수 있다.
- 확정 또는 결제 대기 상태에서 사용하는 객실만 재고에 반영한다.
- 결제 실패 또는 예약 취소 시 점유한 객실을 복구한다.
- 일반적인 중복 예약 검증은 MVP에 포함한다.
- 정확히 동시에 들어오는 요청에 대한 락 전략과 동시성 테스트는 다음 고도화 버전에서 적용할 수 있다.

### 취소

- MVP에서는 체크인 이전의 확정 예약만 취소할 수 있도록 단순화한다.
- MVP의 환불 정책은 전액 취소를 기본으로 하며, 취소 수수료와 부분 환불은 이후 버전에서 다룬다.

## 9. 상태 초안

### 예약 상태

```text
PENDING_PAYMENT  결제 대기
CONFIRMED        예약 확정
CANCELED         예약 취소
EXPIRED          결제 시간 만료(추후 버전)
COMPLETED        숙박 완료(추후 버전)
```

### 결제 상태

```text
READY      결제 준비
PAID       결제 완료
FAILED     결제 실패
REFUNDED   전액 환불
```

MVP의 실제 주요 상태 전이는 다음과 같다.

```text
PENDING_PAYMENT
├─ 결제 성공 → CONFIRMED
└─ 결제 실패 → CANCELED + 객실 복구

CONFIRMED
└─ 예약 취소 → CANCELED + 결제 취소 + 객실 복구
```

## 10. 권장 백엔드 구조

기능 구현 시 여러 도메인의 흐름을 조율하기 위해 다음 계층을 기본으로 고려한다.

```text
Controller
→ Facade
→ Service
→ Repository
```

예약 생성 흐름 예시:

```text
ReservationController
→ ReservationFacade
   ├─ RoomAvailabilityService
   ├─ ReservationService
   └─ PaymentService
```

- Controller: HTTP 요청·응답과 입력 검증
- Facade: 예약·객실·결제의 전체 유스케이스 조율
- Service: 각 도메인의 정책과 상태 변경
- Repository: 데이터 저장 및 조회

MVP의 기능 수는 작지만 계층별 책임을 분리하여 이후 실제 결제와 동시성 제어를 추가할 때 대규모 리팩터링이 발생하지 않도록 한다.

## 12. 아직 팀 회의가 필요한 항목

다음 항목은 확정된 사실로 간주하지 않는다.

- 정확한 기술 스택과 버전
- 인증 방식
- 최초 관리자 계정 준비 방식
- 객실 재고 데이터 모델
- 결제 모의 구현 방식
- 실제 PG 도입 여부와 PG사
- 예약 결제 대기 시간
- 예약 취소 가능 시점
- 환불 처리 방법
- 동시성 제어 기술
- 배포 환경
- API URL과 요청·응답 형식

AI는 위 항목에 대해 하나의 방식을 확정된 것처럼 작성하지 말고, 선택지와 장단점을 제시한 뒤 팀의 결정을 요청해야 한다.

## 13. 다른 AI에 전달할 작업 지침

아래 지침을 이 문서와 함께 다른 AI에 전달한다.

```text
당신은 RoomPick 최종 프로젝트를 돕는 개발·기획 AI다.

1. 이 문서의 '확정한 MVP 원칙'과 'MVP에서 제외하는 기능'을 최우선 기준으로 따른다.
2. 현재 MVP에는 검색 기능이 없으며 관리자가 숙소와 실제 객실을 등록한다. 검증에는 최소 1개씩 사용한다.
3. 요청받지 않은 검색, 리뷰, 찜, 쿠폰, AI 추천 등의 기능을 MVP에 임의로 추가하지 않는다.
4. 새로운 기능을 제안할 때는 '현재 MVP 필수', '다음 버전', '도전 기능'을 구분한다.
5. 기능 수는 최소화하되 예약·결제·취소 과정의 데이터 정합성과 예외 처리는 생략하지 않는다.
6. 설계나 코드를 작성할 때 Controller → Facade → Service → Repository 책임 분리를 우선 고려한다.
7. 확정되지 않은 정책이나 기술은 임의로 결정하지 말고 선택지·장단점을 설명한 뒤 질문한다.
8. AI가 만든 결과물은 팀이 검토하고 수정하기 위한 초안이며, 팀이 내린 최신 결정이 이 문서보다 우선한다.
```

## 14. 회의용 짧은 설명

> RoomPick은 기능을 최소화한 MVP를 먼저 배포하고 이후 버전별로 확장하는 숙박 예약 서비스다. 첫 MVP에서는 관리자가 숙소와 실제 객실을 등록하며 검색 기능은 구현하지 않는다. 회원은 등록된 객실의 상세 정보를 확인하고 날짜를 선택해 예약·결제·취소할 수 있다. 숙소·객실 수정·삭제, 동시성 고도화, 검색, 실제 PG, 성능 최적화와 AI 기능은 MVP 이후 버전에서 순차적으로 추가한다.
