# 모니터링 툴 의사결정 (Prometheus + Grafana)

관련 이슈: #82 ([W2 고도화] 모니터링 툴 적용)

이 문서는 모니터링 도구로 무엇을 골랐고, 왜 그렇게 정했는지 정리한다.

## 1. 왜 필요했나

배포는 자동화됐지만, 앱이 잘 돌아가는지는 헬스체크(정상/비정상)만으로 확인했다.
장애가 나도 로그를 뒤지는 것 말고는 원인을 알 방법이 없었고, CPU·메모리·응답시간
같은 지표는 그 순간이 지나면 다시 볼 수 없었다.

## 2. 무엇을 골랐나

**Prometheus(지표 수집) + Grafana(대시보드 시각화)** 를 선택했다.

| 후보 | 왜 안 골랐나 |
| --- | --- |
| Datadog 등 유료 SaaS | 기능은 좋지만 MVP 단계에서 비용 부담이 큼 |
| AWS CloudWatch | 서버(EC2) 지표는 볼 수 있지만, JVM 힙 메모리 같은 앱 내부 지표 연동이 오히려 더 번거로움 |
| 지금처럼 로그만 확인 | 장애 원인을 사후에 재구성할 수 없어 근본 해결이 안 됨 |

Prometheus + Grafana는 무료고, Spring Boot의 Actuator 기능이 표준으로 지원해 별도
연동 코드 없이 바로 지표를 뽑을 수 있으며, 기존 서버에 컨테이너로 얹기만 하면 돼서
지금 규모에 맞았다.

## 3. 어디에 설치했나

새 서버를 따로 만들지 않고, 앱이 이미 떠 있는 EC2 서버에 Prometheus·Grafana
컨테이너를 같이 띄웠다. 비용은 안 들지만 앱과 서버 자원(CPU·메모리)을 나눠 쓰게
되므로, 서버 사양을 한 단계 올려(`t3.micro` → `t3.small`) 여유를 확보했다.

## 4. 안전하게 쓰기 위해 한 것

지표를 보는 도구가 오히려 보안 구멍이 되지 않도록 다음을 적용했다.

- 앱의 지표 확인용 포트(`8081`)를 실제 서비스 포트(`8080`)와 분리하고, 서버 내부
  통신으로만 접근 가능하게 해서 외부에서는 아예 접근할 수 없게 막았다.
- Prometheus·Grafana는 보안그룹(방화벽 설정)에서 지정된 IP만 접속을 허용하게 했다.
- Grafana는 관리자 비밀번호를 반드시 지정해야만 켜지게 해서, 기본 비밀번호(`admin`/
  `admin`)로 뜨는 상황을 막았다.

## 5. 데이터는 얼마나 보관되나

컨테이너를 재시작해도 지표 기록이 남도록 별도 저장 공간(Docker volume)에 보관한다.
다만 서버(EC2 인스턴스) 자체를 삭제하면 기록도 함께 사라진다 — 별도 백업까지는
이번 범위에 포함하지 않았다.

## 6. 하지 않기로 한 것

Grafana의 데이터소스·대시보드를 코드로 자동 설정해두는 것(provisioning)을 두 번
시도했다가 두 번 다 되돌렸다. "왜 자동화가 필요한지"를 먼저 정하지 않고 만들기부터
해서 방향을 잡지 못했기 때문이다. 지금은 처음 설치할 때 사람이 화면에서 직접
설정하는 방식을 유지한다.

## 7. 도입하면서 같이 발견한 문제

모니터링을 붙이려고 서버 사양을 바꾸며 재시작했다가, 원래부터 있던 배포 설정
실수(앱 컨테이너와 Redis 컨테이너가 서로 다른 Docker 네트워크에 떠서 연결이 끊기는
문제)를 우연히 발견해 함께 고쳤다.

## 8. 결론

지금 단계에서는 비용 없이 바로 붙일 수 있고 Spring Boot와 잘 맞는 Prometheus +
Grafana가 가장 적합했다. 접근 범위(포트·IP)는 최대한 좁혀놨고, 필요성이 불분명한
자동화(대시보드 자동 설정)는 미뤄뒀다. 트래픽이나 팀 규모가 커지면 유료 서비스
전환을 다시 검토한다.

## 9. 이후 변경: Prometheus·Grafana·Kafka를 별도 인스턴스로 분리

Kafka가 추가되면서 앱, Redis, Kafka, Prometheus, Grafana가 서버 1대(`t3.small`)에
전부 몰리게 됐다. Kafka는 그 자체로도 메모리를 1GB 안팎 쓰고, 대기열 처리량이
늘어날수록 더 많은 메모리를 쓰게 되는데, 이게 앱이 쓸 수 있는 메모리와 직접
경합하는 구조였다.

그래서 3절에서 "새 서버를 따로 만들지 않는다"고 정했던 결정을 뒤집고,
Prometheus·Grafana·Kafka를 `roompick-kafka-monitoring`이라는 별도 서버(`t3.small`)로
옮겼다. Redis는 앱과 강하게 묶여 있어 그대로 앱 서버에 뒀다.

두 서버는 같은 네트워크(VPC) 안에서 사설 IP로만 통신하고, 허용된 서버만 접근할 수
있도록 방화벽(보안그룹)을 제한해뒀다. 즉 인터넷에 새로 노출되는 포트는 없다.
분리하기 전에 쌓여있던 Prometheus 지표 기록과 Grafana 대시보드는 옮기지 않고
새로 시작했다.
